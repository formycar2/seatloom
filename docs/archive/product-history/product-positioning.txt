| 项目 | 内容 |
|------|------|
| 文档 | Product Positioning v1.0 |
| 状态 | Draft |
| 更新时间 | 2026-04-24 |

## 一、核心定义

> SeatLoom 是一层本地优先的 AI 项目连续性系统，用来把异构 agent 工具中的 session、证据、交接与状态，收束成一个可恢复、可审计、可持续推进的项目工作面。

这一句话锁定了四个关键约束：

- **"一层"而非"一个平台"**：SeatLoom 不做替代，只做收敛。Codex、Claude Code、Cursor CLI 各自仍是执行主体，SeatLoom 是它们之上的连续性薄层。
- **"本地优先"**：项目数据随项目目录落地，不依赖云端服务即可工作。可迁移、可离线、可审计。
- **"连续性系统"**：品类定义。SeatLoom 要解决的根本问题是"跨工具、跨 session、跨时间的项目连续性"，而非"管理 agent 集群"。
- **"收束成工作面"**：用户不需要在多个终端窗口间搬运上下文、追踪状态、手工交接。所有关键信息收束到一个 inbox + 一条 timeline + 结构化 handoff。

## 二、SeatLoom 不做什么

这不是谦虚，是边界。以下每一项都是主动选择不做的：

| 不是这个 | 原因 |
|----------|------|
| 不是另一个 coding agent | 写代码是 Codex、Claude Code、Cursor CLI 的事。SeatLoom 不生成代码。 |
| 不是另一个 IDE | SeatLoom 不与 VSCode、JetBrains 竞争工作台。它提供的是 IDE 之外的协作工作面。 |
| 不是 runtime orchestrator | SeatLoom 不接管 agent 进程的调度、资源分配、沙箱管理。它只附着、捕获、重建上下文。 |
| 不是 swarm 框架 | 不以 "100+ agent 自主进化" 为卖点。SeatLoom 聚焦于少量角色的可靠协作，而非大规模自主集群。 |
| 不是云端 SaaS 平台 | 本地优先意味着核心功能在离线状态下可用。云端能力（如同步、远程触发）是增强项，不是基本盘。 |
| 不是 Agent 中台 | SeatLoom 不定定义"跨组织 agent 统一管理"的野心。它解决的是一个更窄、更痛的问题：**一个项目里，多个 agent 工具的连续性怎么保住**。 |

## 三、SeatLoom 成立的前提假设

如果以下假设不成立，SeatLoom 的价值基础会动摇：

### 假设 1：AI 编程工具将长期异构共存

Codex、Claude Code、Gemini CLI、Cursor CLI、GitHub Copilot 各有优势场景。没有单一工具能在所有任务上胜出。用户会持续地在不同任务间切换工具。

**证据**：当前重度用户已普遍同时使用 3-5 个 CLI agent 工具。这不是过渡态，而是 AI 编程工具市场的基本结构。

### 假设 2：项目级连续性无法由任一工具单独提供

每个工具的原生 session 记忆是私有的。Claude Code 不知道 Codex 做了什么，Cursor CLI 读不到 Gemini CLI 的 transcript。这种隔阂是架构性的，不会因为某个工具增强了自身的 memory 能力而消失。

**推论**：即使某个工具在未来支持了"项目级长期记忆"，它也只能覆盖自己内部的连续性。跨工具的交接、证据链、治理规则，仍然需要独立于工具的一层。

### 假设 3：重度用户确实有上下文搬运的痛点

在 3-5 个终端窗口之间复制粘贴代码、错误信息、需求描述、测试结果，是一种真实存在且消耗巨大的体力劳动。这个痛点不是臆想的，是可观察、可统计的。

### 假设 4：用户愿意为本地数据主权和控制力付费

本地优先意味着用户保有对项目数据的完全控制。对于独立开发者、小型技术团队、隐私敏感项目，这是一个真实的价值点。

**如果以上四条假设中有两条以上被证伪，SeatLoom 需要重新审视其存在基础。**

## 四、五个铲子：SeatLoom 的核心能力主轴

SeatLoom 不靠"更聪明"取胜，而是靠五个具体的工程能力：

### 铲子 1：Attach（附着）

用户不需要换工具。SeatLoom 附着到正在运行的 CLI agent session 上，从外围捕获其输入输出，不要求篡改底层工具的内部状态。

**它回答的问题**："我有 4 个已经在跑的终端窗口，能不重新启动就把它们接进 SeatLoom 吗？"

### 铲子 2：Capture（捕获）

自动收集每个 session 的 stdout、stderr、transcript、diff、test results、decision records。用户不再需要手动保存或复制粘贴日志。

**它回答的问题**："刚才那个 agent 干了什么？输出在哪？我不想去翻滚动缓冲区。"

### 铲子 3：Rehydrate（上下文重建）

当用户把一个角色从 Claude Code 切换到 Codex 时，SeatLoom 自动组装一个 LaunchPack——包含当前 WorkItem、最近 Artifact、最近 Handoff、Checkpoint、适用规范——注入新 session 的起始上下文。

**它回答的问题**："我要让 Codex 接手 Claude 的工作，但不想从头解释一遍背景。"

### 铲子 4：Replay（回放）

基于 append-only 的 Ledger（事件账本），可以按时间线回放项目的关键决策链：谁、在哪个 session、依据什么上下文、做了什么、经过什么 gate。

**它回答的问题**："两周前那次 bug 是谁引入的？当时为什么做这个决定？有没有经过测试门禁？"

### 铲子 5：Govern（治理）

将规范、权限、预算、审批从 prompt 里抽出来，落实到 schema 校验、状态 gate、权限矩阵和预算上限上。**MVP 阶段只做最轻量的 gate，不做完整 PolicyPack 体系。**

**它回答的问题**："我怎么确保每个 Handoff 都有验收标准？怎么防止某个 session 消耗 100 万 token 还不停止？"

### 五个铲子的优先级

| MVP 阶段 | 铲子 | 说明 |
|----------|------|------|
| **P0 必须** | Attach | 产品入口，没有附着就没有后续一切 |
| **P0 必须** | Capture | 上下文搬运减少的直接来源 |
| **P0 必须** | Rehydrate | 跨工具连续性的核心能力，最多辨识度 |
| **P0 必须** | Replay | Ledger + Timeline，回答"发生了什么" |
| **P1 轻量** | Govern | MVP 仅做 Handoff 必填校验 + 状态 gate |

Govern 后置不是因为不重要，而是因为治理的有效性依赖于前四个铲子的成熟度。没有捕获就没有可治理的素材；没有重构建治理规则无法跨 session 执行；没有回放治理效果无法验证。

## 五、为什么底层 agent 工具增强后，SeatLoom 仍然成立

这是一个必须回答的战略问题。如果 Claude Code 某天原生支持了"项目级长期记忆"，SeatLoom 还有没有价值？

### SeatLoom 的退化路径

SeatLoom 不是赌上游工具永远不进化。相反，它假设工具会越来越强。但它仍然有独立价值，因为：

| 上游能力增强 | SeatLoom 独立保留的价值 |
|-------------|----------------------|
| Claude Code 支持 project memory | 跨工具 continuity（Claude 记不住 Cursor 做了什么） |
| Codex 支持原生 session resume | 项目级证据链独立于工具存在（两周后追查不依赖"那个 session 还在不在"） |
| 所有工具都支持更好的上下文管理 | 治理规则需要工具无关（团队的代码评审标准不应绑死在某个工具的实现上） |
| 某个工具成为绝对主导 | 历史数据跨工具可迁移（不能因为换工具就丢失项目历史） |

### 底线

SeatLoom 最差的情况下可以退化成两件事：
1. **跨工具的项目级 Ledger + Timeline**（单一工具即使再强，也覆盖不了其他工具里发生的事情）
2. **工具无关的 Handoff + Governance 薄层**（团队的流程规范不随工具变迁而丢失）

只要工具异构存在，SeatLoom 就有独立价值。如果未来某一天真的只剩一个大一统的 AI 编程工具，且它完美覆盖了所有连续性需求——那 SeatLoom 的使命本身就完成了，这不是失败。

## 六、SeatLoom 的第一阶段 moat（竞争壁垒）

SeatLoom 的壁垒不是"比 agent 更聪明"，而是：

| 壁垒 | 说明 |
|------|------|
| 项目级留痕 | 跨工具、跨 session 的完整 Ledger，不依赖任何一个工具的日志格式 |
| 跨工具连续性 | 从一个工具到另一个工具的上下文重建能力，这是任何单一工具都不会做的事 |
| 结构化交接 | Handoff 不是聊天片段，而是有 schema、有目标、有签收的正式责任转移 |
| 本地数据所有权 | 所有数据随项目目录落地，可检查、可迁移、可回放，不锁定到任何云端平台 |
| 渐进采用 | 用户可以从 attach/timeline 开始感受价值，不被要求先学全套对象模型 |

## 七、渐进采用模型

| 模式 | 用户行为 | 用户看到什么 | 需要理解的概念 |
|------|---------|-------------|---------------|
| **Mode 0: Attach** | 附着已有的 agent session | Timeline + Inbox | 无（自动生成） |
| **Mode 1: Run** | `seatloom run "fix bug"` | 后台隐式创建 Session/WorkItem/Ledger | 隐式，不暴露 |
| **Mode 2: Collaborate** | 显式创建 Handoff，查看 Review Queue | Handoff 草稿 + Inbox + Timeline | Handoff、WorkItem（按需） |
| **Mode 3: Govern** | 配置 Pipeline、PolicyPack、Gate | 完整的治理视图 | Pipeline、Gate、PolicyPack |

**核心原则**：顶层概念可以埋在架构里，但不能一开始就怼在用户脸上。用户第一眼看到的必须是 timeline 和 inbox，不是 Seat / Session / WorkItem 的定义。

## 八、四个场景化生命体征

SeatLoom 是否"活下来了"，不看对象模型多完整，而看这四个场景是否成立：

### 生命体征 1：跨工具切换不需重写上下文

> 你把一个角色从 Claude Code 切到 Codex 或 Cursor CLI 时，不用重新人工写一遍背景，系统能自动注入足够上下文继续干活。

### 生命体征 2：Session 中断后项目不断

> 某个 session 中断、失忆、跑偏后，项目不是跟着断，而是能从 checkpoint + context pack + ledger 恢复推进。

### 生命体征 3：早上一眼看全局

> 你早上回来时，不需要盯 4 个窗口，只看一个 inbox 和一条 timeline，就知道哪里卡住、哪里待批、哪里已完成。

### 生命体征 4：两周后可回溯决策链

> 两周后追查某个改动时，你能回答"是谁、在什么上下文下、依据哪些证据、经过什么交接和 gate 做了这个决定"。

**这四个生命体征是 MVP 的终极验收标准。如果做不到，SeatLoom 就只是一个结构良好的管理外壳。**

## 九、第一阶段核心验证指标

| 指标 | 目标值 | 测量方式 |
|------|--------|----------|
| 上下文搬运次数减少 | ≥ 50% | 对比同一 WorkItem 在有/无 SeatLoom 时的手动上下文搬运次数 |
| 跨工具切换恢复时间 | ≤ 5 分钟 | 从用户发起切换到新 session 接收到完整 LaunchPack 的时间 |
| 4 个窗口信息收束 | 1 个 inbox + 1 条 timeline 即可覆盖 | 用户能否在不切换窗口的情况下回答"现在什么状态" |
| 两周后决策回溯 | 完整还原率 ≥ 80% | 随机抽取已完成 WorkItem，回溯其关键决策链的完整度 |
| Mode 0 用户学习成本 | 首次使用 ≤ 10 分钟即可看到价值 | 新用户从安装到第一次在 timeline 中看到有意义信息的时间 |

## 十、止损条件

如果以下任一情况发生，MVP 被视为失败，需要重新审视产品方向：

1. 两个主力工具的 attach + capture 成功率低于 90%
2. 跨工具 rehydrate 后的新 session 完成同一任务的效率低于手动搬运上下文的情况
3. Mode 0 用户需要学习超过 3 个新概念才能看到 timeline/inbox
4. 早期用户在试用一周后，仍然更倾向于手动在窗口间复制粘贴
