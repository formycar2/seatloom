## 2. 方向我选了后者,理由

派单让我选:**枚举 NavRail 双向核对**,还是**在 `provenanceForTab` 里对未声明的页签
返回诚实状态**。

**我选后者,而且两层都做了。**

理由:

- **枚举只能覆盖 NavRail。** 这个产品还有其他渲染页签的地方,
  枚举一处漏一处,而漏掉的那处照样落到 seed。
- **函数层能拦住任何未声明的页签**,不管它从哪来。
- nav 层仍然要,因为"有人加了页签忘了声明"这件事,**必须在加页签的那个动作上失败**,
  而不是等某个界面渲染出来才暴露。

## 3. 改动

### ① 新增 `Provenance` 状态 `not-declared`

```ts
if (LEDGER_TABS.has(tab)) return backendHydrated ? 'ledger' : 'fixture';
return 'not-declared';
```

文案明确说这是**"没人说过",不是"这是假数据"**:

> 没有任何名单说明这一页的数据从哪里来 —— 不是数据库,不是 tmux 镜像,
> 也不是手工基线。这是「没人说过」,不是「这是假数据」。
> 如果你是新加了这一页,请在 LIVE_TAB_BACKING 里声明它读什么;
> 在声明之前,请不要把这里显示的任何行当成实时数据,也不要把它们当成示例数据
> —— 它们的来源是未知的。

**关键是它不说"是假的"。** 说"是假的"是一个关于数据的断言,而这个状态是一个
关于**声明**的断言。混淆这两者正是原缺陷。

### ② `seed` 的 meta 保留,但 fall-through 没了

派单让我想一下 Flux 的 M-1(删掉 seed 分支 → 24/24 全绿)和我上一轮删死分支之间的矛盾。

**我的答案:这两件事不矛盾,因为"不可达的分支"和"可达但没人到达的分支"不是一回事。**

- **seed 的 meta 保留** —— Flux 说得对,死代码描述一个正确的状态,比没有代码好,
  等那个状态真来的时候。删了它,等真有一个 seed 驱动的界面落地时,措辞要从头写。
- **fall-through 删掉** —— 让一个未声明的页签**借用** seed 的措辞,才是骗人的那一步。
  我上一轮删的是"读起来像活规则但永远不执行的门";这一条是"未声明的页签默认
  拿到一个关于它数据的断言"。**方向相反,结论一致:不能因为代码路径短就让它
  替一个没人做过的决定发言。**

### ③ nav 按钮加 `data-tab-id`

label 会翻译,rail 在多个断点下折叠,`title` 有时不存在。
**两者都不是"这是哪个页签"的稳定把手。**

没有它,"加页签忘声明"这个变异**在哪都失败不了** —— 测试拿不到 id。

### ④ 测试走真实 DOM,不写死名字

派单明确禁止:

> 不要写一条只对当前页签清单成立、加一个页签就要改测试的断言
> (比如把八个名字写死在测试里)—— 那正是最初那条断言的性质,它强制了排除。

**我读 `nav button[data-tab-id]`,不写死任何名字。** 所以**加页签这件事本身
就是让这条测试要求声明** —— 而不是让某个人记得去改测试。

## 4. 变异:四个,全红

| # | 变异 | 结果 |
|---|---|---|
| 1 | **往 NavRail 加页签不声明**(Lyra 跑的那条) | **1 红** |
| 2 | `not-declared` 落回 `seed` | **1 红** |
| 3 | 去掉 `data-tab-id`(测试空转) | **1 红** |
| 4 | 硬编码名单 | **我没那么写** —— 理由在测试注释里 |

变异 3 值得单独说:它证明这条测试**不是空转**。如果 nav 按钮上没有稳定 id,
`tabIds` 会是空数组,`expect(undeclared).toEqual([])` 会**因为空数组而通过** ——
一条永远绿的测试。加了 `expect(tabIds.length).toBeGreaterThan(0)` 之后,
拿不到 id 本身就是失败。
