## 1. 要解决的是什么

操作者反馈三条:纵向平铺不易扫读、信息密度不足、交互需设计。

翻译成信息架构语言,问题是:**旧版把一个"队列"渲染成了一个"信息流"**。每条派单独占一张高约 90px 的卡片,一屏只能放 4-5 条;卡内事实按重要性纵向堆叠(状态、标题、摘要、时间),于是"横向比较"——这一屏里哪个席位最忙、哪条已经等了最久、哪条优先级最高——必须靠肉眼逐张读。筛选条是唯一的交互,回答不了队列真正被问的问题:*每个席位在干什么、什么卡住了、下一个该动什么*。

队列类界面的一等公民是**行**,不是卡片。所以重设计的核心决定只有一句:**一行一条派单,一屏二十条,所有可比较的事实进列。**

## 2. 为什么是密表,不是看板

派单原文给了两个候选:紧凑表格/行布局(可排序),或按状态的看板。我选了密表,看板明确否掉,理由是数据形态:

- **派单的主内容是长文本。**标题 + payload 指令动辄一两行中文,四列看板每列只有 ~250px,会把操作者真正要读的指令截成 Telegraph 体。密表给标题列分配剩余全部宽度,长文本仍有 ~500px。
- **看板消灭了跨席位比较。**车队饱和时操作者要问的是"先拉哪条",答案跨所有席位;看板把比较降级成"记住每张卡的位置",而密表的优先级列一列就给完了。
- **看板暗示了它不具备的能力。**派单状态由调度器拥有,操作者不能拖卡改状态——一个可拖的看板会做出这个虚假承诺(与 UM0 审查里"优先级必须诚实地不可操作"是同一条原则)。

看板唯一优于密表的地方(状态聚类的视觉强度)由密表的状态列 + 状态筛选条 + 按状态排序补回。

## 3. 设计决策与理由

### D1 — 一行一条,八列密表

`席位 | 状态 | 优先级 | 派单(标题+摘要) | 时长 | 发出 | 依赖 | 操作`,`table-fixed` + `colgroup`,标题列吸收剩余宽度。行高 ~38px,一屏 20 条,纵向扫读密度提升约 4 倍。

`COLUMNS` 单一声明同时驱动 `colgroup`、表头单元格和排序行为——避免"列宽和控制项漂移"这类只在重构时爆发的 bug(实现时确实先踩到过一次:表头漏了标题列导致列错位)。

### D2 — 五列可排序,默认序即调度器拉取序

可按 席位 / 状态 / 优先级 / 时长 / 发出 排序。**默认排序不是随手选的升序,而是复刻调度器自己的拉取序**:席位 → 生命周期(进行中→就绪→阻塞→完成)→ `priority DESC` → `issued_at ASC`(见 `crates/seatloom-core/src/db/repositories.rs:412` 的 `ORDER BY`)。操作者看到的默认顺序,就是车队接下来会执行的顺序——筛选和排序都不改变这个承诺。

点击表头在该列的默认方向与反向间切换(优先级/时长默认降序,席位/状态/发出默认升序),激活列显示箭头,非激活列 hover 时才显形,避免八列八箭头的噪音。

### D3 — 分组保留,但组头变成 triage 行

UM0 审查的 S1 是对的:"按席位分组"是这份界面最有价值的决定,它匹配操作者的心智模型("这个席位要干什么")而非数据库的("存在哪些派单")。所以分组保留为默认,但组头从"一个名字"升级成**一行状态条**:席位名 + 等宽字形 seatId + 该席位各状态计数(进行中 1 · 就绪 2 · 阻塞 1)+ 总数。操作者读一行就知道这个席位要不要管,不用读它下面的行。

另外提供 **全局平铺** 模式:跨席位单表,用于"先拉哪条"这类必须横向比较的场景。两种模式共用同一套列定义和排序,切换不丢筛选/排序状态。

### D4 — 已完成默认折叠,但不是藏起来

完成项是唯一"不再需要操作者注意力"的状态,所以它是唯一被折起来的。默认收成一行 `已完成 N 默认折叠`,点开是一张完整的表(不是灰掉的历史墙)。筛选条切到"完成"时自动展开。若当前筛选下只剩完成项,空状态会直接说"无待处理的派单 · N 项已完成已折叠"并给一个展开按钮——不会让操作者以为数据没了。

### D5 — 行内展开替代详情页

点行在原地展开完整 payload + 出处网格(编号 / 发出者 / 项目 / 状态 / 发出 / 开始 / 完成 / 依赖)。派单内容是一段指令,值得读全文,但不值得为它跳一个新页面再跳回来。展开状态按 dispatch id 持有,5s 刷新不会把它冲掉(UM0 审查 S4 的第一条)。

### D6 — 交互补齐:搜索、再派发、暂停、变更高亮

- **搜索**:标题 / payload 指令 / 席位 / 编号四路匹配。筛选条的计数始终描述整个收件箱而非当前筛选——计数条是摘要,表格是选择,两者不混。
- **再派发**(UM0 审查 S5 的闭环):每行一个 `CopyPlus`,把席位/标题/指令/优先级带进"新建派单"表单并聚焦标题框。"就绪"从"一个状态"变成"一个可执行的提议",且不引入任何新的后端语义。
- **暂停自动刷新 + 上次刷新时刻**(S4):5s 轮询保留为默认,但操作者可以一键暂停(暂停时仍可手动刷新),并始终看得到"上次 hh:mm:ss"。自动刷新只有从不消耗操作者的位置时才配得上信任。
- **变更高亮**(S4):轮询间状态翻转的行短暂高亮 ~2.6s(就绪→进行中),让"状态变了"被看见,而不是靠操作者从一张被静默替换的列表里推断。
- **依赖只作计数**(S3):`↑N` 加 tooltip 列出 `kind: value`,不画边。依赖边跨组边界,画出来只会变噪音。
- **空状态分三种**:从未派单 / 搜索无匹配 / 该状态为空——三种各自指向不同的下一步操作。

### D7 — 视觉一致性与诚实的细节

严格沿用 TimelineView / V1 AppShell 的 token(`bg-background`、`bg-card`、`bg-secondary`、`border-border/40`、`text-text-primary/secondary`、`rounded-xl`、`text-[10px] font-black uppercase tracking-widest`),没有引入新色板;状态仍是色+字,从不只靠色。

席位色片由 seatId 哈希确定性生成,同一席位在刷新和不同视图间保持同色,操作者可以学会"青色那个是 Nimbus"。时长列一个数回答"这条在当前位置待了多久":完成=实际耗时,进行中=已进行,就绪/阻塞=已等待;tooltip 说明语义。优先级只做视觉强调(P≥5 上主色),**不提供改优先级的控件**——排序是视图能力,重排是调度器所有权。

## 6. 未做 / 后续建议

- **没有组件测试基建的先行投入记录**:jsdom + @testing-library 已是声明依赖但此前无组件用例,本次首次使用;建议后续把"每视图一组交互回归"作为默认实践。
- **阻塞原因仍拿不到**:`dispatches` 表只有依赖边,没有"为什么阻塞"的字段。UM0 审查 S2(行内阻塞原因)需要后端先落一个 blocker 原因列,前端才能诚实展示——现在只显示依赖计数,不编原因。
- **行操作仅"再派发"**:完成/取消等写路径由调度器拥有,前端不提供(诚实原则)。若将来开放,应在同一操作列追加,并保持"禁用带原因"而非隐藏。
- **列宽固定**:八列合计 560px + 弹性标题列,在 <900px 宽度下会挤。桌面操作台场景可接受;若要支持窄屏,建议按断点隐藏"发出/依赖"两列,而不是横向滚动表格。
