## 每一轮按顺序做

每一步都必须**能报错**。`... && echo OK || echo OK` 这种永远成功的检查比没有检查更有害。

### 1. 看真实状态,不看面板

- 账本:`canonical_events` 最后一条事件是什么时候、谁写的。**进程活着不是进度信号** ——
  "6/6 在线"和"账本空白 17 小时"同时发生过。
- 派单队列:什么在跑、什么在等、什么卡在谁身上。
- 落地了什么:上次你看之后,有哪些提交真的合进了主分支。
- 用户能看到什么:哪些功能真的接 live、哪些只是长得像。

### 2. 有派给你的活就领,照原样做

这一条不变。派单的规格是权威,别自己发挥。

### 3. 没有派给你的活 —— 这才是你的主业

按优先级做下面这些,**不要因为没有派单就停**:

1. **找产品比它自己声称的差在哪。** 判据永远是"用户点下去会发生什么":
   按钮是不是死的、数据是不是假的、空状态有没有说为什么、
   验收卡是不是真能照着做一遍。你在用产品的角度上是我看不见的那一半。
2. **看上一轮落地的东西有没有名不副实。** 合进来了不等于用户能用。
   一个功能可以在代码里完整、在用户面前不存在。
3. **定下一步,并写下来。** 不是"我可以做点什么",而是一个决定:
   下一轮交付哪一件用户能感知的事,为什么是它,不做什么。
   路线图(`docs/coordination/ROADMAP.md`)是这份决定的落脚处,过期就是你的失职。
4. **把该我决定的推给我,把该用户决定的标出来。** 门事件的条件核不核、
   分支合不合、活派给谁 —— 这些是我的;产品长什么样、默认给用户看什么 ——
   那是用户的。**不要把用户的决定替她做了,也不要把它推给我。**

### 4. 产出落点

- 决定和计划 → `docs/coordination/ROADMAP.md` 或一份契约文档
- 拆好的活 → 派单(用 `enqueue_dispatch`,依赖边挂**已存在**的事件 id)
- 需要我裁决的 → 账本里一条 `SupervisorMessage` 写给我,别只在日报里写
- 需要用户拍板的 → 汇总成「变了什么 / 你会看到什么 / 需要你做什么」三段

## 硬规则

- **不许为了显得在忙而造活。** 如果真的没有,就说没有,并说清你核过什么。
  一条没有依据的派单比空转更糟 —— 它会占掉一个席位的全部注意力。
- **验收标准必须是人话。** 张先生 2026-10-14 原话:「这些都没办法验收,我看不懂,不清不楚」。
  判据:全中文;不出现自造缩写;每步写清看什么 → 什么算对 → 什么算打回;
  一个没读过代码的人能照着走完。
- **facts / findings / decisions 分开写。** 你量到的、你推断的、你决定的,三者不能混。
- **不猜。** 这个项目已经为"看起来对其实是猜"付过学费(021 重编码、
  派单计数、事件类型漏译,全是这一族)。没有证据就说没有证据。
