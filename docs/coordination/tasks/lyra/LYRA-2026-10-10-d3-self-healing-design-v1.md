## 0. 一句话

**团队出问题(失败/卡住/停摆)时,系统先自愈;自愈不了,把"什么卡住、已尝试什么、建议你做什么"推给你。**
底座 = Onyx 013 状态机(failed/cancelled/retry + blocked→ready 触发器,Lyra 已签署)+ D2 验收环
(打回→自动重派)+ scheduler 已有的 cycle/stall 检测。

## 1. 场景拆解(每组:用户可见结果 / 验收标准 / 一步验法)

### S1 席位失败自述(seat says "I tried, couldn't")
- **机制**:`complete_dispatch(outcome="failed", reason)` → `in_flight→failed`(终态)或预算内
  `→ready`;事件 `SeatDispatchFailed` / `SeatDispatchRetried`(013 已签,均在 D2 卡分支的 Rust 上)。
- **用户可见**:派单页该单显示"失败(原因)",不再是假 done,也不再水久占槽。
- **验收标准**:失败必带 reason;终态不可变;in_flight 槽释放;全程可回放。
- **一步验法**:制造一个 failed 单 → 页面见失败徽标+原因 → 时间线见 `SeatDispatchFailed`。

### S2 自动重试(瞬时故障自愈)
- **机制**:`max_retries` 预算内 `in_flight→ready` + `retry_count+1`;按 013 签署,**不设粘性,
  任何合格席位可拉**;预算耗尽才 terminal failed(硬上限,绝不无限循环)。
- **用户可见**:单自动回到 ready(可能被别的席位接手),重试血缘在时间线可见。
- **验收标准**:每次重试一个事件;耗尽即终态;`retry_count` 不超 `max_retries`。
- **一步验法**:预算=2 的单失败一次 → 见回 ready + `SeatDispatchRetried` → 再失败两次 →
  terminal failed(徽标变化)。

### S3 卡死回收(in_flight 死锁 — 本里程碑最高风险项)
- **问题**:席位崩溃/重启/放弃 → `in_flight` 水久楔死,部分唯一索引阻断该席位**一切**后续拉取
  (我此前 milestone backlog 的 P1;013 只给了终态,没给"怎么到达终态"的回收路径)。
- **选型(待你裁决,见 §3)**:
  - (a) **席位会话启动自对账**(推荐主路径):席位起来时,本席位 `in_flight` 且非当前实际任务 →
    标记 `failed`(reason="seat restarted mid-dispatch")或提请 issuer cancel。零轮询,事件驱动。
  - (b) **issuer 侧 `cancel_dispatch`**(D2 已交付,监督兜底):发起人/监督席位可随时强杀释放。
  - (c) 超时 reaper:**已拒绝**——轮询式,架构在 cc92714 已明确否弃。
- **用户可见**:席位重启后收件箱立即恢复可拉;被回收单有明确终态+原因,不静默消失。
- **验收标准**:重启不丢后续可拉性;回收动作有事件;**不误回收在途单**(只回收"重启时仍挂 in_flight
  且会话未认领"的)。
- **一步验法**:造一个 in_flight 单 → 重启该席位会话 → 见该单变 failed(带原因)且该席位能拉新单。

### S4 取消与打回环路(发起人控制面)
- **机制**:`cancel_dispatch`(仅 issuer,非终态→cancelled,释放 in_flight 槽);打回→自动重派
  已在 D2 交付并验。
- **用户可见**:发起人可撤回派错的单;被打回单自动回到该席位(带你的原话反馈)。
- **验收标准**:取消仅 issuer;取消 in_flight 即释放槽;重做单 priority 插队(+10)且血缘可查。
- **一步验法**:取消一个 ready 单 → 见 cancelled + 不再被拉取;打回流程即 D2 已验证路径。

### S5 停摆/成环检测与告警(团队级,用户感知面)
- **机制**:scheduler 已有 cycle/stall 检测 → 升级为**告警对象**(什么卡住、涉及哪些单、已尝试的
  自愈动作、建议的用户动作),路由:Aegis → 用户(IM,北极星通道,D1 复用其投递机制);PC UI 告警区
  作为下钻后备(D2 同款分层)。
- **用户可见**:"团队卡住了:X;已尝试:重试 N 次/无合格席位;建议:改依赖 / 重派 / 取消"。
- **验收标准**:同一 stall 只告警一次(不轰炸);每个告警带≥1 个可执行建议;stall 解除后有解除通知。
- **一步验法**:构造全 blocked 停摆 → 收到一条带建议的告警 → 按建议动作解除 → 见解除通知。

### S6 告警打扰边界(升级阈值)
- **机制**:同类告警聚合;瞬时失败(重试成功)**不推用户**;只有"需要用户决策"的才推(重试耗尽/
  停摆/成环/取消冲突);升级阈值 + 静默期。
- **用户可见**:风平浪静时零消息;真卡住时恰一条。
- **一步标准/验法**:构造"失败一次+自动重试成功" → 用户零告警;构造"重试耗尽" → 恰一条。
