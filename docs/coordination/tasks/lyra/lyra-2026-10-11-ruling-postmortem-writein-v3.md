## 1. 裁决原文(截至目前收到的全部条款)

1. **重派一张失败过的单,必须把导致它失败的那个前置挂成依赖边。**
2. **席位在失败报告里写的「在 X 成立之前不要重派」,其他席位必须遵守。**

四条澄清(同为裁决组成部分):

- 失败报告里的"不要重派"**不是抱怨,是可执行的前置条件,对其他席位有约束力**。

**判据 4 的解读(本席执行口径)**:一个前置要不要图禁,不看它多重要,看**下游单是否真的
会调用该前置对应的能力**。会调用的(如本 lane 真的要 open_topic/remember 打 live),
其前置必须是依赖边或实测事实,散文担保无效;不会调用的,挂了也是演戏。这与"门必须挂在
真实调用上"同构——ev-typed-memory-tools-landed 的正当形态本就是一次真实 remember
成功,而非代码落地。v3 遵此:它确实要调用写入能力,故 019-applied 挂为边;进程面前置
已被 v2 实测成立(且 pull 时守卫复测),无需边。

**Aegis 可执行判据(原话)**:会调 → 必须有 live 可用的门;只读代码/写文档 → 代码落地就够。
对照本夜 lanes:写库 lane 真调 open_topic/remember 打 live → 门 = 019 已应用 live
(即 v3 的依赖边);冒烟/建卡/方案供稿/读模型验收等只读代码或写文档 → 代码落地事件
(如 ev-typed-memory-tools-landed)即是合格门。**原单的设计错误由此定性**:给一条真调
live 的 lane 挂了代码落地事件当门——门型与 lane 性质不匹配。
