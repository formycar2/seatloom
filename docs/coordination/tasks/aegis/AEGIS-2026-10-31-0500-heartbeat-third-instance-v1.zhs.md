## 变了什么

### 三件验绿单回来了,两件 pass,而 Flux 又抓到两条真的

上一轮我发现有三件活做完了、没有 verdict、没有卡,派了 Flux 逐件验。
三件都回来了。**两件我逐条自己复现过。**

**一、待验收卡计数(Mira)** —— pass,但 Flux 抓到一条我复现后确认还在:

把徽章条件从「大于 0 才显示」改成「大于等于 0」→ **15 个测试全绿**。
后果是:一张卡都没有时,「派单」那一项上会挂一个**永远的 0**。

这不只是难看。**一个永远都在的徽章,不能传达任何信息。**
而 Mira 自己的测试文件注释里写着这个假设 ——
「默认空着,这样导航徽章只在测试要求时出现 —— 一个永远在那里的徽章证明不了任何事」。
**那套测试工具整个建立在这个假设上,而这个假设本身没有断言。**

**二、SAMPLE 徽章(Mira)** —— pass,她抓到两条,其中一条她自己已经修了:
那个死分支和两份名单漂移的问题,她把两份名单合成了一份
(从一张推导另一张),所以漂移在构造上不可能了。
我变异验过:往名单里单加一个标签 → 测试红。**这个修法比加断言更彻底。**

**三、原子性测试(Nimbus)** —— pass,而 Flux 抓到的是同一个病的第三次:

他为修「deferred-ness 没断言」而新加的第三个测试,**自己也没有那条断言**。
第三个测试靠 `NOT DEFERRED`(触发器必须立即咬,不能等 COMMIT)
才和第一个测试区分开,而这条性质只写在建触发器的那行 SQL 里。

我复现了:把 `NOT DEFERRED` 改成 `DEFERRABLE INITIALLY DEFERRED` → **3 个测试全绿**。
改完它和第一个测试形状一模一样,没有任何东西注意到。

**为什么会复发:补测试的时候,补的是「场景」,不是「性质」。**
两个场景确实不同,所以写第三个测试是对的。但让它们不同的是那条性质,
而它只存在于一行 SQL 和一段注释里。**场景是可见的,性质是隐含的。**
写测试的人看见场景不同,就以为测到了不同的东西。

已派 Nimbus 补那条对称的断言。
