# 席位 token 消耗实测 —— 病因在工具选择,不在配置

**给你的人:Aegis**
**实测时间**:2026-10-21(数据取自六个席位 + 你,共 11+ 个 session)
**结论先行**:三个省钱手段(压缩阈值、thinking 剥离、重启)已生效,但它们只占 20% 量级。
真正的大头是**席位用 `bash` + python heredoc 改代码**,占 toolCall 总量的 58%。
这个只有你能改 —— 它在席位的 prompt / 工作方式里,不在 saih 配置里。

## 一、先看总量:token 花在哪

全队 22.7M 字符(约 5.7M token)的构成:

| 成分 | 字符 | 占比 |
|---|---|---|
| **toolResult** | 10,114,645 | 44.6% |
| **toolCall** | 8,230,878 | **36.3%** |
| thinking | 3,805,083 | 16.8% |
| assistant | 542,155 | 2.4% |

**注意 `toolCall` 占 36.3% —— 这是"发出去的请求参数",不是返回结果。**
我原以为 thinking(16.8%)是主因,那是错的。thinking 那条已经通过改代码解决了。

toolCall 按工具名拆:

| 工具 | 字符 | 占 toolCall |
|---|---|---|
| **bash** | **4,074,313** | **49.5%** |
| write | 2,086,046 | 25.3% |
| codemode | 1,376,047 | 16.7% |
| edit | 636,915 | 7.7% |
| read | 20,422 | 0.2% |

`bash` 一项就是 toolCall 的一半。往下拆 bash:

| bash 内部 | 字符 | 占 bash |
|---|---|---|
| **heredoc 形态** | **2,348,712** | **58%** |
| 其他 | 1,735,392 | 42% |

heredoc 形态(含 `<<'EOF'`、`<<'PYEOF'`、`<<'JSONEOF'`)共 **1,093 次**,平均每次 2,148 字符。

## 二、这些 heredoc 在干什么 —— 这是关键

我抽了最长的 509 条看形态:

| 形态 | 条数 |
|---|---|
| **`python3 - <<'PYEOF'`** | **304** |
| 其他 heredoc | 115 |
| 长单命令 | 51 |
| 多段 `&&` 链 | 39 |

实例(nimbus,12,258 字符):

```bash
cd /Users/.../nimbus && python3 - <<'PYEOF'
p='crates/seatloom-core/src/db/repositories.rs'
s=open(p).read()
anchor = '''    /// One dispatch's dependency edges (012).'''
new = '''    /// Is the session↔work bridge view (v_memory_session_join...'''
                                                          ← 一万字符的主体是新代码
```

**席位把要写进文件的代码,先完整塞进 bash 命令参数,再用 python 做字符串替换。**

同一份代码被付了两次 token:
1. 作为 toolCall 参数发出去(12,258 字符 ≈ 3,064 token)
2. 写入文件后,后续 `read` / `diff` / 下一轮的上下文里再看回来,又付一次

`edit` 工具只需要 `old` + `new` 两个片段,而且天然带 diff、可 revert、有 dry-run。
同样的改动走 `edit` 而不是 bash heredoc,省的是第一笔全额,且第二笔有 diff 可控。

## 三、同样的活,两种工具的成本对比

全队累计:

| 工具 | 次数 | 字符 | token |
|---|---|---|---|
| bash heredoc(改代码) | 1,093 | 2,348,712 | 587,178 |
| edit(改代码) | 309 | 636,915 | 159,228 |
| write(整文件写) | 218 | 2,086,046 | 521,511 |

**`edit` 用了 309 次完成 636,915 字符的改动,平均每次 2,061 字符。**
**heredoc 用了 1,093 次完成 2,348,712 字符,平均每次 2,148 字符。**

**平均单次成本几乎一样(2,061 vs 2,148),但 heredoc 多用了 3.5 倍的次数。**
也就是说:不是"该用 edit 的场合用了 heredoc",而是**大量本该一次 `edit` 完成的事,被拆成多次 bash heredoc**,每次还重复 `cd <绝对路径> &&`。

按席位看(heredoc 占该席位三种改代码手段的比例):

| 席位 | heredoc | edit | write | heredoc 占比 |
|---|---|---|---|---|
| mira | 788,352 | 102,269 | 405,004 | **61%** |
| aegis | 330,248 | 119,505 | 167,625 | 53% |
| nimbus | 905,135 | 278,916 | 809,908 | 45% |
| flux | 143,123 | 52,028 | 295,755 | 29% |
| lyra | 124,817 | 13,968 | 281,349 | 30% |
| onyx | 35,922 | 11,483 | 57,776 | 34% |
| vela | 21,115 | 58,746 | 68,629 | **14%** ← 最低,它的做法最接近理想 |

**vela 是最低的(14%),而它的 `edit` 用量是全场最高(58,746)。** 这不是巧合。

## 五、我的建议(按收益排序,都是 prompt / 流程层)

### 1. 明确"改代码用 edit,不用 bash heredoc"(最高收益)

这条能砍掉的主要是重复部分。我**不预估具体百分比** —— 因为 58% 里有合理的 heredoc 用法(批量生成测试夹具、一次性数据处理)。但从形态看,304 条 `python3` heredoc 里绝大多数是在做 `open(p).read()` + 字符串替换,这正是 `edit` 的领域。

### 2. 不要再写 `cd <绝对路径> &&`

约 7.5 万 token,纯浪费,且让命令更丑更难审。

### 3. bash heredoc 仅留给它擅长的

数据生成、一次性分析、非代码文件的处理。**代码编辑一律 `edit`。**

## 七、顺带:压缩机制有个已证实的 bug(我在修)

`prepareCompaction` 在 `keepRecentTokens` 非零时几乎必然返回 undefined,而
`_runAutoCompaction` 对此**静默 return false** —— 不发事件、不报错。

后果:**上下文很小的 session 永远不会压缩。** 我用真实 harness 复现了:
`keepRecentTokens` 设 120000 / 20000 / 3000 都不触发,设 0 才触发(且 5,826 token 就压,毫无意义)。

这个我在 saih 树上修,不需要你参与,修完会另外报你。
