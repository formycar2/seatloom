## 1. 目标、范围与结论

响应 `docs/coordination/tasks/aegis/AEGIS-2026-11-02-1200-arch-review-dsh-superagent-v1.zhs.md`。
这是架构建议的交付，不是实现验收，也不是迁移上线许可。产品权威入口仍是 `docs/PRODUCT_TRUTH.md`；本文不覆盖人工授权、人工点击验收、现有界面形态与席位职责。

**建议不添加可写的 stage 列，也不重做调度系统。先把“执行生命周期”“需要谁做什么”“授权依据”分开，由同一套后端规则从记录中给出答案。**

最小改进顺序：

1. **先统一待办读模型**：复用人工决策、验收卡与结构化阻塞提示，列表和计数用同一份结果；不知道执行情况时就显示未知。
2. **再补派单授权依据与命令入口校验**：先利用现有派单 payload 和事件 payload 记录有版本的依据，不把 JSON 记录当成权限边界。
3. **再完善外部动作的持久回执与恢复**：优先处理合并成功但落库失败等跨系统窗口，不因已有 NOTIFY 就推倒现有唤醒链。
4. **最后才考虑外部事件准入与模型研判**：默认只产生建议；不自动获得写库、合并或变更授权的能力。

**本轮建议的第一步不改 schema，因此没有迁移或回滚 SQL。** 后续若确需独立授权表、执行尝试表或外发队列表，必须另交成对迁移/回滚脚本并在沙箱验证；本文不预占迁移编号，不提供未经验证的占位 DDL，也不授权先改库后补脚本。

### 3.1 DSH 授权实现还有两条不能遗漏的边界

**配置权限不全是机器可验证的人类许可。**

- `src/app/tools/main.ts:249–265` 提供 `orchestrator_settings_save`，schema 包含 policy/eval；“须有明确的人类配置请求”写在 description，工具参数没有该请求的可信凭证。
- `src/app/settings.ts:33–52` 对 executor 环境和 source 账户有 panel-origin guard，对 policy/eval 没有同样的 guard。
- `src/app/http.ts:75–79,201,237` 的 loopback/同源头检查用于限制网页来源；本地请求可走 `'panel'` 保存路径。它不是操作者身份认证，更不是防本地 worker 提权的边界。

这不是已完成的攻击复现，也不意味着其所有权限检查无效；它说明**不能拿“宿主执行规则”推导出“模型永远不能改规则”**。SeatLoom 必须把授权写者与席位进程分离，而非只换一个工具名或端口。

**Mandate 的内容不变，与撤销是否永久落盘是两件事。**

`src/core/evals.ts:306–315` 创建授权快照；人的 stop 写入 Ticket 的 human-ended 标记。重新验证失败走 `tickets.ts:311–315` 的 `refuse`：清空待投递消息、交还路由，所读实现未写独立的持久 revoked 标记。已有测试验证当前策略无效时不恢复，未据此证明“策略恢复有效后仍永久拒绝”。因此本文只确认当前策略重验和人停单保持，不把文档的 revoked 一词扩大成永久吊销保证。

## 4. 建议的架构分工

```text
人的命令 / 已批准的有限委派       外部消息 / 文档 / 运行事实
              │                         │
       可信身份与授权依据检查      记录、关联、提供上下文
              │                         │
              └───── 建议/澄清（不能授予权限）
                               │
                 统一命令入口：校验项目、范围、版本、依赖
                               │
                 派单 + 生命周期事件（同一数据库事务）
                               │
                   现有调度器 / waker / MCP 领单
                               │
             结构化进展、阻塞、决策、交付、独立验收
                               │
                   人点击 Accept → 合并与落库恢复流程

          上述事实 → 共享读模型 → 现有总控面板、计数、通知
```

保留 PostgreSQL、Rust 核心、React/Tauri 和席位 tmux，不迁往 DSH，不引入另一个 Router agent 替代 Aegis 的裁决职责。借鉴的是小接口、事实只存一份、命令统一校验；不是把系统拆出更多服务。

### 4.1 第一项：统一“需要我做什么”，不要加可写 stage

复用的事实源：

- `operator_decisions` 中 pending 且 decider 为当前操作者的行：欠一个明确决定。
- `acceptances` 中 pending 的行：欠一次交付验收；派单本身可能已经 done，不能被“只看进行中派单”筛掉。
- `prompt_instances` 中仍 active、需要人工的提示：保留已记录的操作与会话引用；没有记录就不能猜测。
- `dispatch_dependencies`：说明尚欠的前置事实；不自动等同于欠人输入。
- 会话/领单数据：分别说明已领单与最近观测，`in_flight` 不直接翻译成“模型正在运行”。

第一步只增加共享的后端查询/DTO 组装和既有面板消费，不增加持久列。所有待办保留原对象 kind/id/project/actor，沿用原动作入口。计数、列表、通知使用相同项目、操作者、过滤规则和快照；分页时明确 total 与当前页，不拿截断后的列表长度充当全量数字。

**一项工作可同时欠决定和验收。** 展示可以按“需决定、待验收、需排障、依赖等待、已领单、待领单、结束”选主要标签，但完整 obligations 列表不能被互斥标签丢掉。系统故障自动重试中单独展示，不计作必须人工回答。

当前 `operator_decisions.target` 是文本；`repositories.rs:1967–2043` 写入的事件以 decision 为 subject，没有强制 dispatch 关联。因此先做项目级待办联合列表。只有可靠的显式关联才显示到具体派单；禁止按标题相似、同席位或最新一条问题猜关联。补结构化关联是后续契约工作，不在此处假装已有。

**不会自动释放在等人的席位名额。** 一席位只能一条 in_flight 是数据库约束；只增加显示层不能改变它。是否允许等人时接另一单，会影响恢复、上下文和并发，须另做执行尝试/占槽设计与验收，不能顺手改 status。

### 4.2 第二项：派单带授权依据，但先说清记录与强制的区别

建议新派单先在现有 `payload` 增加有版本的授权记录契约，由命令入口从可信来源构造，不能接受模型自称的 `approved: true`：

| 字段语义 | 必须回答 |
|---|---|
| basis_ref + basis_digest | 哪次真实的人类命令或既有有限委派；引用哪一版，内容变化能否发现 |
| issuer + grantee + project | 谁授给谁、在哪个项目；来自可信身份，不从正文抽取 |
| allowed_operations + resources | 允许的动作和对象；自然语言说明只作补充 |
| parent_ref + bounds | 子派单依据什么父授权；不能扩大项目、对象、动作、有效期或再委派能力 |
| policy_revision + checked_at | 使用哪版规则，在何时验证 |

这只是建议契约，不是已发布 API。先复用事件引用、角色绑定与委派；是否足以表达资源范围，须由后续契约评审决定，不能把现有自由文本 constraints 当成可执行策略。

命令入口至少在 **入队、领单、重试/恢复及受保护的外部动作前**验证相应权限，数据库时钟判有效期；版本检查与状态提交之间要有事务/并发控制。换策略后是否允许继续安全收尾，必须显式规定，不能把所有停单都等同于 kill 进程。

历史派单没有依据时标记“未记录”，不补造人的批准；继续执行前经授权方确认。已有授权下的有限分派不要求人逐条重新批准，但被拒的动作绝不能借子派单扩大权限。人工 Accept 交付仍是另一个独立决定，开工许可不含合并许可。

**数据库权限是启用条件。** 若 worker 仍可拿同一凭据直写授权数据或改 schema，仅在 MCP 里加验证不能防绕行。后续需先列出真实写入口和角色权限，在沙箱证明席位不能自行签发或扩大授权，再申请受审计的 live 变更。没有这一步，只能宣称“授权溯源”，不能宣称“安全边界已建成”。

还有一个应优先修的入口不一致：`src-tauri/src/commands/dispatch_cmds.rs:119–130` 的 UI 派单包装硬编码 `human:supervisor`，并使用默认项目；相比 `acceptance_cmds.rs:61` 读取显式 operator_ref，它缺少同样的身份来源约束。不能把“来自 UI”当成“已证明是哪位人授权”。本轮只指出代码事实，未运行该路径。

### 4.3 第三项：单一命令规则 + 可恢复副作用

DSH `src/core/engine.ts` 的命令统一 `repo.atomic`，`src/app/outbox.ts:26–36` 把回执与待发送效果同事务记录。这种模式值得借鉴，但数据库事务不能包住 Git、进程、网络。

SeatLoom 已有派单/事件/NOTIFY 同事务及 waker 重连、周期补扫，不必为唤醒另造一套消息总线。已有 `channel_action_receipts` 是动作回执，不等同于带待发送/重试语义的 Outbox。

更紧要的静态发现：`acceptance_cmds.rs:91–111` **先 Git merge，再 decide_acceptance**。如果后者失败，可能出现代码已合并、卡仍 pending。本文未注入故障复现，故判为需验证的跨系统失败窗口，不报告为已发生事故。

建议后续针对每次人工 Accept 保存稳定操作标识、固定被审 head/base 与操作者依据；失败恢复先核 Git 已完成事实，禁止盲目再合并；重复点击不能生成第二次效果。这里需要状态机与故障注入设计，若新增操作日志表必须另交迁移/回滚。不得把“后台自动重试”扩大成人尚未批准的新合并。

单一写者指每类事实有一个规则实现，不是一个全能进程、一个共享高权限账号。可先从各入口共同调用的 Rust 命令服务收敛，不要大规模搬目录掩盖真实权限问题。

### 4.4 第四项：外部事件准入与研判，暂缓建设

DSH 的 Source 游标、稳定 Trigger id、上下文订阅和输入回执适合未来接外部项目事件；先明确何为事实、何为命令。canonical_events 是内部事实账本，不能直接用任意外部消息冒充领域事件。

未来模型只给“建议做什么/为什么/需要澄清什么”，确定性检查决定是否有资格进入命令路径。初次试运行应是我们定义的全只读观察：没有新派单、没有工作进程、没有外发消息。既有明确人令继续走原路径，不让新观察器暗中接管。

上下文订阅不扩大授权；陌生人的跟帖不能自动恢复被人暂停的工作。通知可去重、合并重复进展，不能隐藏待验收、授权失败、未完成投递或到期未答的决定。保留已有推送要求，不把健康空白面板替代“全队在做什么”。
