## 3. 清洗方案(五种 harness → 一种规范格式)

这是技术上最难的一段,因为 **5 种 harness 的记录格式互不相同**:

| harness | 格式特点(实测) |
|---|---|
| codex | `rollout-*.jsonl`,主体是 response_item |
| claude-code | `*.jsonl`,类型有 system / user / attachment / assistant / custom-title / agent-name / file-history-snapshot / last-prompt |
| cursor | **没有 cwd 字段**(13 个全部),要从内容里推项目归属 |
| gemini | **没有 cwd 字段**(9 个全部) |
| stepcode | `*.jsonl`,格式接近 claude-code |

**方案:先归一化成统一的 turn 流,再提炼。** 统一流的字段:

```
{ seq, ts, role(user|assistant|system|tool), kind, text, refs }
```

- **cursor / gemini 没有 cwd** → 不猜。要么从内容里找到明确的仓库路径证据才归类,要么**单独放一个"归属不明"主题**,不硬塞。这条和整个项目的纪律一致:猜出来的归类比没有归类更糟。
- **`file-history-snapshot` / `attachment` 这类元数据行** → 不当正文。上次审计已经抓到过:有 3 条记忆的"证据"指向 `{"type":"mode",...}` 这种元数据行。**归一化阶段就要把它们过滤掉,不能留给提炼阶段。**

## 8. 补充:恢复卡的输入必须是「git 状态 + 会话尾巴」(张先生纠正后的定稿)

### 8.1 为什么两个都要

| 输入 | 给什么 | 不给什么 |
|---|---|---|
| git 状态 | 什么在进行中:分支、脏文件、未跟踪、最近提交 | 为什么这么定、卡在哪儿、下一步干什么 |
| 会话最后 N 轮 | 已确认的决策、卡住的确切原因、下一步的明确动作 | 完整的历史(那才需要全量清洗) |

### 8.2 一张恢复卡的形状(以 cn-gpu-infer-fabric 为实例)

```
项目            cn-gpu-infer-fabric
当前任务        收尾更新 Step-5-Preview 销售报价 v2.1
已确认的决策    平台托管 API 售卖;不设实施费报价项;私有化部署不作为报价枚举;
                专属机器/专属容量属于容量或 SLA 保障,不等于私有化交付
进行到哪儿      模板已按最新脚本重新生成;定向 10 passed、全量 280 passed、Excel 压缩包完整
卡在哪儿        最后一项校验命令没执行到内容检查 —— zsh 不展开压缩包内部通配路径,不是模板错误
下一步          改用明确的 XML 文件列表核验下拉枚举与关键方案状态
                → 确认工作区差异只含本轮应有的修改 → 提交
git 状态        main,最后提交 2026-08-13,3 个已跟踪脏文件 + 35 个未跟踪
来源会话        codex/rollout-2026-08-12T17-12-22-019ff53e...(最后修改 2026-09-29,669 轮中取末 12 轮)
```

### 8.3 「最后 N 轮」取多少

建议 **N = 12~20 轮**,判据是**取到出现以下任一项为止**:

- 一个明确的「下一步 / 接下来我会」表述
- 一个 Handoff Summary 或等价收尾段
- 一个被用户确认/否决的决策

取不到就往后扩,但**不超过 50 轮** —— 超过还取不到,说明这个会话没有干净收尾,恢复卡里要明说「无明确下一步」,而不是硬编一个。

**恢复卡是轻的,清洗是重的,两者不互相替代:**
