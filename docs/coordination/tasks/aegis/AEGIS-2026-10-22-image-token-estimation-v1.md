## 先说这个 bug 是什么(在 saih/pi 的 harness 里,不在 SeatLoom 里)

`saih/pi/packages/coding-agent/src/core/compaction/compaction.ts:275`

```ts
const ESTIMATED_IMAGE_CHARS = 4800;
```

**它把每张图片按 4800 字符估算(约 1200 token),无论那张图实际多大。**

Aegis 在自己的 session 上实测(不是推测):

| 类别 | 大小 | 占比 |
|---|---|---|
| `toolResult:image`(6 张) | **8.35MB** | **67%** |
| 工具回传文本 | 1.54MB | 12% |
| 工具调用 | 1.15MB | 9% |
| 思考块 | 1.08MB | 9% |
| 正文 | 0.29MB | 2% |

**均条 1.4MB。** 按 chars/4 粗算,一张约 35 万 token,而这个函数当它 1200。

**低估约 300 倍。**

## 后果:阈值改了也白改

2026-10-21 把压缩触发阈值从 983,616 降到 220,000(那份改动是对的、必要的)。
但**因为图片被低估,那 6 张图在阈值判定里只算 7,200 token** ——
压缩因此始终不认为上下文已经很大,图片一直留着,每回合重发。

Aegis session 实测:压缩命中 12 次,`image` 在文件里仍出现 29 次,16MB 没降下来。
**压的是别的,图一直在。**

## 张先生的裁定就是解法方向

> 「看完图之后做总结,就不要再继续使用原图的信息了」

**图的价值在看完那一刻。** 之后它只是占地方的 base64,而且每回合重发。

## 要做的事

### 一、把估算改成按实际大小(必须)

`ESTIMATED_IMAGE_CHARS` 这种常量不能再用。改成按 image 块的**真实 payload 大小**算:

- 图片块的 data 长度就是真实大小,拿得到就用它
- 拿不到(比如只有引用)时,宁可高估也不要低估 ——
  高估只会让压缩早一点触发,低估会让它永远不触发
- 保留一个上限兜底(比如 1 张图最多算多少),防止一张巨型图直接把整个会话判爆

### 二、按裁定实现"看完就丢"

压缩时,`image` 块的处理要明确:**它不是不可丢的原文**。

具体要你设计的:一旦某个回合已经有 assistant 对这张图的结论(文字),那张图在后续回合
就没有信息增量了。所以压缩时可以把**已被文字结论覆盖的图**替换成一句短说明
(比如「此处原有一张截图,结论见上文」),而不是原样保留 base64。

**注意**:不是无条件丢所有图。最近一两回合的图可能还要用(比如正在对比两张截图)。
丢的判据要写清楚,并且要保守 —— 丢错东西比费 token 更糟。

### 三、必须有测试,两个方向

派单的硬要求:

1. **一张大图必须被算成大**:构造一个 1MB 级的 image 块,断言 `estimateTokens`
   返回的量级和它相称(不能是 1200)
2. **压缩后不再保留已被结论覆盖的图**:构造"截图 → assistant 结论 → 更多回合"的场景,
   断言压缩产物里那张图的 base64 不再存在,而结论文字还在
3. **最近的图不许被误丢**:同一测试里要有一个反例 —— 还没有任何结论的图必须保留
4. **不许为了让测试过而把图片全部无条件丢弃** —— 那就把功能砍了,
   和这个 bug 是同一种病(用删掉问题来"解决"问题)

## 验收

- `estimateTokens` 对 1MB 图片的估算量级正确(不是 1200 token)
- 压缩后:有结论覆盖的图不再携带 base64;无结论的图保留
- 上面四个测试都在,且**两个方向都有断言**
- 既有压缩测试全部仍通过(不许改断言)
- harness 类型检查与测试全过;测试不许恒真

## 明确不做

- 不改压缩阈值本身(220,000 是 10-21 定的,那一刀是对的)
- 不做"禁掉所有图片" —— 有些判断必须看图,张先生没说禁,他说的是"看完就丢"
- 不动 SeatLoom 自己的代码(这是 saih/pi harness 的仓库)
- 不合并、不自己开验收卡
