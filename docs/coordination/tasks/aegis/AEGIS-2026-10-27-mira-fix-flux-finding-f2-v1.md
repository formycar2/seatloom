## F2(他实测出来的,不是推断)

**`supervisorSyncLost` 是单个可空槽位。** 查询的 `.catch` 写
`{kind:'never-answered'}`,订阅的 reporter 随后用 `{kind:'stale'}` 覆盖它 ——
**后写的赢,而订阅的 rejection 落在更晚的 microtask**。两个 reporter 不知道
彼此存在。

实测四种组合:

| 组合 | 界面 |
|---|---|
| 查询 OK + 订阅 OK | 没有条 |
| 查询 OK + 订阅失败 | 黄 stale,无重试按钮 |
| 查询失败 + 订阅 OK | 红 never-answered,有重试 |
| **查询失败 + 订阅也失败** | **只有 stale —— 更糟的那个被藏了** |

最后那行的后果,他的原话:

> 操作者被告知"你有一个答案,只是它不说话了",而事实是"你从来没有得到过答案"。
> **而唯一有用的那个动作(重试)没有提供。**

严重度他定 **P3**(不是 P2),理由也说清了:两条一起失败意味着事件总线大范围坏了,
这时候 stale 条的重启建议仍然对,重试大概也会失败。**但消息是错的,
而且查询的错误原文 —— 操作者能拿去找人的那份证据 —— 不见了。**

## 修复方向(他给的,而且不是他设计的)

**照你自己已经为两个订阅通道做的那套来**:`lostChannels` Map +
"两条通道都断了"那行。两个订阅通道都能共存,查询和订阅没道理不能。

**具体怎么设计由你定**,Aegis 不替你设计。

## 要你做的

把两条失败路径做成能共存的,而且**更糟的那个不能输**。要想清楚:

1. 两个都失败时,界面显示什么形状?(红?黄?还是红的底 + 说明订阅也断了?)
2. 重试按钮该出现吗?(查询那次读可以重试;订阅那条你说过不该重试。
   两个都坏的时候呢?)
3. 查询的错误原文还看得见吗?—— 那是操作者能拿去找人的证据
4. 文案要说清"从来没有答案"这个事实,不能退回"答案停止维护"

## 判据

- 四种组合都给出实测输出(照 Flux 那张表,一张张对)
- **查询失败 + 订阅失败**那行:更糟的不被藏、错误原文在、该有的动作在
- 写测试钉这条(Flux 是用 jsdom 驱动真实 App、注入 api seam 测的)
- 证明测试会红:把修法贴回"单槽位覆盖",测试必须 FAIL

## 明确不做

- 不许让"后写的赢"继续存在,哪怕这次赢的那个看起来更合理
- 不许把错误原文丢掉 —— 它是操作者唯一能拿去找人的东西
- 不许改 ⌘K / 内嵌面板渲染逻辑
- 不许顺手改别的 `.catch`
