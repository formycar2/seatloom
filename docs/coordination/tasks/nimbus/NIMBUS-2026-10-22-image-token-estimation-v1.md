## 一句话

图片 token 估算从「每张一律 4800 字符」改成「按 base64 真实长度算,拿不到就按上限算」;
「看完就丢」落在请求路径上,判据是**已被文字结论覆盖、且对话已经翻页** ——
两个条件都满足才换成一句短说明,否则原样保留。

## 一、估算改成什么

`compaction.ts` 原来:

```ts
const ESTIMATED_IMAGE_CHARS = 4800;   // 每张图一律按 ~1200 token 算
```

现在按 `block.data.length` 算 —— `data` 就是发给 provider 的 base64 串,它的长度就是
请求真实携带的大小。三个边界:

| 情况 | 取值 | 为什么 |
|---|---|---|
| 有 `data` | `min(data.length, MAX_IMAGE_CHARS)` | 真实大小。上限以下的图(包括正常 resize 过的)完全按实际算,不会被截断 |
| 没有 `data`(引用,非内联字节) | `MAX_IMAGE_CHARS` = 8MB | **宁可高估**。这一支正是原 bug 最致命的地方:一个未知大小的图被当成 1200 token,会让 `shouldCompact` 跳过一次其实巨大的请求 |
| 一张巨图 | 同上限截断 | 防止单个块决定整个历史的形状:不设上限时,一张 resize 失败透传的原图会让切点落在它后面,把它之前的内容全丢掉 |

上限取 8MB,高于 `normalizeToolResultImages` 的默认 4.5MB,所以正常路径永不被截断,
只有病态情况被截 —— 而且是朝「仍然非常大」截,不是朝「便宜」截。

**两个失败模式不对称**:高估只让压缩早一点触发;低估让它永远不触发,阈值形同虚设,
图片每回合重发。所以拿不准时一律往上取。

## 二、丢图的判据(这是本次的核心设计)

丢图**不在压缩里做**,而在请求路径上(`session-manager.ts` 的 `buildSessionProjection`,
和 `dropStaleThinkingBlocks` 并列)。

**为什么不放在压缩里**:压缩决定「重发多少历史」,这个决定「每次重发多贵」。图片的价值
在看完那一刻被提取,之后每回合重发的是同一份 base64 —— 和 thinking 块完全同族。
`dropStaleThinkingBlocks` 已经为同一个目的站在同一条路径上,这里是它的邻居,不是新机制。

**判据,两个条件都满足才丢**:

1. **已被文字结论覆盖** —— 该图之后存在某个 assistant 消息产生了非空文字。
   没有结论的图一律保留:一张还没被读、还没被回答的截图绝不静默消失。
2. **对话已经翻页** —— 在**那个结论之后**又开始了新的回合。

第 2 条是我在实现中被自己的测试抓出来后改的,值得单独说。第一版判据写的是
「该图之后有结论」+「该图不是最后 N 张图」。测试一跑就发现两个问题:

- 「最后 N 张」这个写法在**只有一张图**时永远成立,于是任务包自己的场景
  (截图 → 结论 → 更多回合)永远修不好 —— 那 6 张图的实际场景也一样修不好。
  这不是保守,是失效。
- 更要紧的是:操作者正在对比两张截图时,模型已经描述过它们(「两张几乎一样」),
  但那一回合**仍是当前主题**。若只看「有结论」就丢,「再仔细看看第二张」就没东西可看了。

所以保守底线改成**相对于结论**,而不是相对于图:结论之后有新回合,才说明旧图变成了历史。

## 三、测试怎么证明两个方向

新文件 `packages/coding-agent/test/image-token-estimation.test.ts`,9 个测试:

**估算那一侧(4 个)**

| 测试 | 断言 |
|---|---|
| 1MB 图 | `> 200_000` token(旧值是 1200)**且** `< 300_000`(防止变成无意义放大) |
| 4 字符小图 | `=== 1` —— 修的不是「图都很大」,是「按实际大小」 |
| 无 payload 的图 | `> 200_000` —— 拿不到就往高取,不复活原 bug |
| 64MB 巨图 | `<= 8MB/4` 且 `> 1_000_000` —— 上限生效,单块不能决定历史 |

**丢图那一侧(5 个)**

| 测试 | 断言 | 方向 |
|---|---|---|
| 已结论且已翻页 | base64 不在、结论文字在、原位有「此处原有一张截图」 | 该丢的丢 |
| 无结论的图 | base64 **在** | **反例**,让上面那条有意义 |
| 正在被对比的两张 | 两张 base64 都**在** | **反例**,保守底线 |
| 同一张图,翻页后 | base64 不在、结论在 | 边界确认 |
| toolResult 里的图(截图工具) | base64 不在、结论在 | 实测那条路径(均条 1.4MB 的就是 `toolResult:image`) |

两个反例是这次的重点:没有它们,「该丢的丢」那条测试在一个**无条件丢所有图**的实现上
同样会通过 —— 而那正是任务包明令禁止的(「用删掉问题来『解决』问题」)。

   「低估 300 倍」这个量级错误,不是「精确计费」。要精确需要按 provider 分别建模,
   那是另一件事,我没有顺手做。
