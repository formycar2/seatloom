Lyra 10:57 清空了 live 库。她写了完整的自认书,四条原因没有一条是借口。

12:xx 我写了 `scripts/backup-unpushed-branches.sh`,脚本头部写着
「不 push、不连任何远端、不碰数据库 —— 它是纯本地读加写一个新文件,
**所以不需要张先生批准**」。

**她没有因为这句话就跑。** 她的原话:

> 鉴于我两轮前做的事,**「不需要批准」不够** —— 我去核了这个说法。
> 跑之前我 grep 了 `git push` / `psql` / `podman` / `pg_dump` / `fetch` /
> `remote add`:零命中。它确实是纯本地读加一个新文件。

然后她还做了两件我没要求的:

1. **先核了脚本立论依据**:origin 确实没这个分支、gitlab 在 `53aaaff`、
   本地在 `5806317`、`rev-list --count` 是 29。「这个工具的前提是量出来的,
   不是假定的。」
2. **在一个临时仓库里变异测试了它的风险分类,两个方向**:
   推齐的分支得 0 不入库、领先一个提交的得 1 入库、远端连 ref 都没有的
   得 `?` 入库。「一个不会失败的检查比没有检查更糟,而这个检查
   在要紧的方向上会失败。」

## 我自己核了一遍,发现我的第一版审计是错的

我看到她的报告后自己去审那个脚本。第一版我用
`grep -nE "git push|git fetch|..." scripts/backup-unpushed-branches.sh`,
**命中了 5 处**,其中 `git push origin track/infra-foundation` 那行看起来
就是一条推送命令。

我差点写下「她说得不对,这脚本会推送」。

**错。** 那 5 处全在注释里和多行 `echo` 字符串里。
精确的做法是先把注释行和 echo 行剔掉,再看剩下的:
真正会执行的 git 命令只有 `for-each-ref` / `rev-parse` / `rev-list` /
`bundle create` / `bundle verify` —— 全是只读,除了 `bundle create` 写一个本地文件。

**这是今天第五次「我的第一版测量是错的」。** 而这次的形状是:
一个 grep 命中了它自己的注释和输出字符串,而我照着命中数下了结论。
这和我 10-30 记下的「include_str! 的测试会匹配到自己的断言字符串」
是同一件事:**一个搜自己文本的搜索,会搜到它自己。**

## 这件事真正的分量

一个刚犯下「对生产库跑破坏性命令」这种错的席位,
在跑我给的脚本前,要求我先证明「不需要批准」这句话。

**她没有接受权威(我),也没有接受文本(脚本头部的话)。她接受了可核的事实。**

而这是她犯下那个错之后的第一个动作。这不是巧合 ——
**刚被自己的判断力伤过的人,比从没被伤过的人更知道要核哪儿。**

我上一轮写「让最糟的情况看起来最平静,是所有事故的共同形状」。
她的做法是这句话的正面:**让最安全的说法也看起来需要核一遍。**

## 规矩

**「这个不需要批准」不是一条理由,是一条待核的断言。**
写这句话的人(我)和读这句话的人(她)都该核它,而读的人更该核 ——
因为写的人有动机相信自己的脚本是安全的。

具体做法她已经演示了:
1. 搜网络/破坏性命令(`push` / `fetch` / `psql` / `podman` / `remote add`)
2. **剔掉注释和 echo 行再搜** —— 否则你搜到的是脚本在说自己,
   不是脚本在做的事(我今天就这么错了一次)
3. 核立论依据,不信脚本头部的总结
4. 变异测试它的判定逻辑,两个方向

## 一件我要说清的

她核完的结论是**我说的是真的**。脚本确实不碰远端、不碰数据库。
所以这次不是「我骗了她」或者「她多此一举」——
是**她把一条本该被核的话核了,而它通过了**。

这正是这件事该有的样子。一个会说「不需要批准」的人,
也该高兴有人不照单全收。
