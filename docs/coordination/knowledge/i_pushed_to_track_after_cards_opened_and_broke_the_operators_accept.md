# 我在开卡之后往 track 提了代码,把操作者的 Accept 全卡死了

2026-10-28 05:00 心跳。队列空了,23 张卡 pending,看着像"一切就绪"。
多查了一步:那 23 张卡**现在点得动吗**。

## 答案:点不动,23 张全点不动

三个席位的分支**全部**落后 track:

| 席位 | 卡数 | 落后 |
|---|---|---|
| Mira | 11 | 2 个提交 |
| Flux | 8 | 2 个提交 |
| Nimbus | 4 | 2 个提交 |

而那 2 个提交是**我自己**在开卡之后提到 track 的
(`16e65e3` 补回漏掉的测试、`8c1182c` 记录复发)。

验收门的规则(它拒得对):

> accepting an unsynced branch would merge work that never saw the base's later commits

所以操作者现在点任何一张卡,都会收到一句拒绝。**他不会知道为什么**,
他只会看到"我点了,没反应/报错"。

## 为什么这是我造成的,而且是最糟的那种

时间线:

```
17:02  三张卡开出来(Mira / Flux / Nimbus 的分支都同步过)
19:03  又三张开出来
20:02  又两张开出来
04:00  我发现合并漏了测试 → 提到 track  ← 我把 track 往前推了
       ─────────────────────────────────
       从这一刻起,上面 23 张卡全部点不动
```

**我在开卡之后动了 base,而没同时让卡的主人同步分支。**
这不是"我犯了个错然后去修",这是"我修一个错的时候,顺手把操作者等的东西全锁住了"。

而且特别讽刺:我提那两个提交的动机,是**修我合并漏文件那个错**。
修错的动作本身造成了更大的堵。

## 更讽刺的一层

被卡住的那 23 张里,有一张 `acc-disp-jZg89gwy8YzVOOjdAsxTL`
—— **修的就是"操作者的话显示进别人那一格"那个 bug**。
他报告了 bug,我们修了,验了,开卡了,然后我把他点卡的路堵了。

## 我做了什么

派三个席位同步分支(优先级 99,最高),并 poke 了他们。同步是安全的:
我的两个提交只动了一个 UI 测试文件和知识库文档,和他们改的文件不重叠。

**没做的:没有自己去合他们的分支。** 那是他们的分支,而且合完要重跑门禁 ——
门禁得在他们自己的工作区跑,我跑的不算。

## 判据(以后照这个做)

**往 track 提任何提交之后,必须立刻做一步:**

```bash
# 有没有 pending 的卡,它们的分支是否还包含 track HEAD?
# 每个有 pending 卡的席位,分支都要能回答 yes
git merge-base --is-ancestor track/infra-foundation HEAD   # 在各分支上跑
```

**只要有 pending 卡存在,往 track 提代码就不是一个中立动作** ——
它会给每一张卡加上一道"先同步"的门。

如果必须提(比如修一个阻塞性缺陷),那就**同一个回合里派单让卡的主人同步**,
不要等下一轮心跳。等一小时,操作者就多点一小时点不动的东西。

## 一句话

**"队列空 + 卡多"看起来是最健康的状态,而这次它恰恰是最堵的状态。**
判据不能停在"卡开出来了",要问到"卡点得动吗"。

## 第二次复发,同一天,更严重(2026-10-28 12:17)

上面那段写完(05:20),我以为自己记住了。**没有。**

| 席位 | 卡数 | 落后 |
|---|---|---|
| Mira | 11 | **1** 个提交 |
| Flux | 8 | **9** 个提交 |
| Nimbus | 4 | **9** 个提交 |
| 合计 | **23** | 全部点不动 |

我 10-28 从 08:05 到 12:15 往 track 提了 **8 次**,而每一张 pending 卡都创建于
10-28 04:02 之前。这不是"同步窗口"的疏漏 —— 是我在同一轮心跳里一边处理门的活、
一边往 track 提代码,而卡就摆在那 23 张,我一次都没问它们点不点得动。

**同一个 seat、同一天、同一条规则、第二次。**

## 判据为什么不够

上面写的判据是"提完之后立刻跑一遍 `merge-base --is-ancestor`"。它是一个**记得才跑**的
动作。我 05:20 写下它,08:05 到 12:15 提了 8 次,一次都没跑。

**一条靠记住才执行的规则,不是控制,是愿望。**

## 换成机械的

`scripts/check-cards-clickable.sh`:
查账本里所有 pending 卡,对每一张检查它的分支是否还包含它的 base。
打印一个数字,点不动就 exit 1。它现在跑出来是 `FAIL: 23 of 23`。

`.git/hooks/pre-commit`:往 `track/infra-foundation` 提代码时,如果有 pending 卡会因此
被卡住,直接拒绝提交。它刚被验证过 —— 它拒了我自己那笔提交。

紧急情况的出口是显式的:`--no-verify` + **同一个回合**派同步单 + 在 commit body 里写
原因。出口存在,但它留痕。

## 一句话

**规则写第二遍不等于规则被执行了。第二次犯同一个错的时候,该动的不是措辞,是执行方式。**
