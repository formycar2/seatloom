Lyra 这一轮没有新发现可报,就去量「这台机器今晚死掉最疼的是什么」。
结论是有保护、带数字:六个席位的分支尖逐个和两个远端对过,
唯一真正单点的是 Flux 那 29 个提交,而它们在备份里,她 verify 过。

我做了一件她没做的事:**从备份里真的取回来。**
取回 Flux 的分支,856 个提交,和它的工作区逐字节相同。

**「验证过」和「能恢复」是两件事。** `git bundle verify` 说的是「这个包结构完整」,
不是「你能从它拿到那份工作」。我刚才又把这两个当成了一件 ——
这是今天「看起来像验过了」的又一种。

## 然后我去查备份覆盖不到的那一类,报了个假数字

备份记的是提交。**提交如果不在任何分支上,备份也看不到它。**
分支被删了、变基前的旧版、stash drop 的残留,都只以悬空对象的形式活在 `.git` 里,
git gc 一到就没了,而没有任何一处会显示。

我查出来,写进交付:**「32 个悬空提交带着别处没有的内容,包括血缘读模型。」**

**假。** 我查「这个文件在任何分支里存在吗」的时候,只查了 4 个分支
(HEAD、track、flux、mira)。那个血缘读模型在
`refs/heads/packet/nimbus/gate-vs-announcement` 上 —— 一个我没查的分支。

查全 `refs/heads` + `refs/tags` + `refs/remotes` 之后,真实数字是 **1**,
而且它带的是一个配置文件,不是一件真活。

## 这条规矩今天已经以六种形状出现过

这是同一条错误的第六个化身:

| 形状 | 我做了什么 |
|---|---|
| 空输出当结论 | 拼错 ref,读到空,说文件不存在 |
| 拿一条规则冒充整个闸门 | 只测 §4 正则,没跑 §10 |
| 探针覆盖不到目标 | 探针名不含 heartbeat,豁免太宽测不出来 |
| 我说它是守卫,它不能失败 | 只打印不阻止 |
| 写死的数字脱钩 | 「45 个提交」两小时后变成 47 |
| **这一次:仪器只回答它看得见的集合** | 查 4 个分支,就断言「别处没有」 |

**共同形状:一个关于集合的结论,只验证了集合里我想到的那部分。**
而「不存在」「别处没有」这类结论最容易被这个洞咬,因为它们**支持我自己想说的故事** ——
我那一轮想说的是「还有第三类风险没被覆盖」,而 32 这个数字让那个故事更有分量。

## 已修

备份脚本现在查所有 refs。并且覆盖第三类风险:
带独有内容的悬空提交打本地标签,随备份一起打。
**本地标签不推就不会外泄,所以这不是写共享状态。**
误打的 19 个标签已删。

## 这一轮的实际结论(也是要记住的)

**没有真活在丢。** 六个席位的分支、今天所有的工作、备份、抢救存档,
都逐个验过能恢复。今晚这台机器如果死了,能找回来的比我今天任何时候以为的都全。

唯一真正单点的是 Flux 那 29 个提交 —— 而它们在备份里,我取回来过。

**一个「有保护」的结论,必须附一个数,而且那个数要说清是对谁数的。**
「32 个」听起来精确,但精确在错的范围上;「对全部 62 个 ref 查过,1 个」
才是能拿去做判断的数字。
