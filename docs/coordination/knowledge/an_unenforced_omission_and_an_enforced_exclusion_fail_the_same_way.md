# 修好一个被强制的排除之后,剩下的是一个未被强制的遗漏,而方向一样

SAMPLE 徽章那个缺陷的原貌:一个测试**按名字规定**数据库支撑的页签
恰好是 `[sessions, dispatches]`,于是七个真读 Postgres 的页签
被按在「SAMPLE DATA — not yet from live capture」上。

Mira 修了:两份名单合成一份,从一份推导另一份,漂移在构造上不可能。
我变异验过 —— 往名单里单加一个标签 → 测试红。

Flux 重验,给 pass,但留了一条发现。**我复现了,它还在。**

## 那条发现

往 NavRail 的条目数组里加一个新页签,**不在任何名单里声明它的数据来源**
→ **382 passed。**

后果我写了个探针自己量:

```
provenanceForTab('brandnew', true, 'ready')  →  'seed'
```

`true` 是后端已完全水合。也就是说:**后端正在吐真数据的时候,
那个新页签告诉操作者「这些行是手写的样例」。**

## 他的框架,和为什么我认为它比他自己说的更要紧

Flux 的原话:推导修好的是**两份名单之间的漂移**;
它没有加任何东西去抓一个**两边都没加入的页签**。
原来的缺陷是一个**被强制的排除** —— 一条断言规定集合恰好是那两个,
由此把七个活页签按在 SAMPLE 上。那个没了。
剩下的是一个**未被强制的遗漏**,它因为同样的原因、朝同样的方向静默失败。

他把这条标为比原来的**窄**。我同意窄。但方向是一样的:

> 一个界面说自己的数据是假的,而它是真的。

而这个产品已经被张先生批评过很多次「看起来接着,其实什么都没调」。
一个**新页签默认自称假数据**,正是那个形状的又一条入口 ——
而且它是**默认值**:不需要任何人写错一行断言,
只需要有人加页签时忘了第二处。

## 更普遍的一条

**排除和遗漏是同一个失败的两种方向。**

- 被强制的排除:测试说「只有这两个」,于是别的都进不来。
- 未被强制的遗漏:没人说「都进来」,于是新的进不来。

两者都产生「界面说的和事实不符」。而修掉前者的常用手段
(把集合写死、加一条精确匹配的断言)**恰好是制造后者的原因** ——
我在这条派单里专门写了:不要写一条只对当前页签清单成立、
加一个页签就要改测试的断言,**那正是最初那条断言的性质**。

## 顺带:一个不可达的分支,比没有分支更容易骗人

Flux 的 M-1 是删掉 seed 分支 → 24/24 全绿。他的判断是:
死代码描述一个正确的状态,比没有代码好,等那个状态真来的时候。

Mira 上一轮刚删了一条不可达的分支,理由正是「一个永远不执行的分支
比没有分支更容易骗人」。**两句话都对,而它们指向相反的处置。**

我在派单里让她自己想清楚怎么协调,没有替她决定。
我倾向的看法:分支该不该留,取决于**那个状态可不可能到达**。
`seed` 描述的是「后端不可达、退回内存假数据」——
那是一个真实会发生的状态(她自己的 verdict 里有一条
`backendHydrated ? live : fixture` 就是处理它的),
所以它该留。而 `if (LIVE_TABS.has(tab)) return 'live'` 那条
描述的是「这个页签是活的」,而那个判断已经被前两条分支完全决定了,
它**不可能**再到达 —— 所以该删。

**判据不是「它死不死」,是「它描述的状态还可能发生吗」。**
