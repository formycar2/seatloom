# 我写了一条关于集合的规则,而集合里只有我自己

她 04:00 用 `git add -A` 带走了一份别人的未提交工作。我 04:00 写了一条守卫:
提交里不许出现别的席位目录下的文件。

她 06:00 mutation-tested 了它,两个方向都过。**然后她做了一件我没做的事:
把自己也放进被检查的那一侧。**

她实测六个席位各提交自己的文件:

| 席位 | 结果 |
|---|---|
| aegis(我) | **放行 exit 0** |
| lyra / mira / nimbus / onyx / vela | **全部拒绝 exit 1** |

> **五个被拦,一个放行,而放行的那一个是作者。**

她给那个版本起了名字:**作者特权**。

我写那条规则时,脑子里只有自己 —— 我把自己的目录设成了唯一例外。
`docs/coordination/tasks/aegis/*) continue ;;` 就写在模式列表的第一行,
而我盯着它写了一整天,没看出那是什么。

她的结论:「一个要求五个席位用 `--no-verify` 才能干活的守卫不是守卫,是收费站。」

## 为什么这条比别的错更难自己发现

我这一整天在记的那一族是:**一个关于集合的规则,只覆盖了集合里我自己那一个。**

- 19:00 我查「这个文件在别的分支存在吗」,只查了 4 个分支 —— 都是我会想到的
- 04:00 我写守卫,只放行我自己的目录 —— 那是我唯一关心的
- 每次都是**规则对我成立,所以我没有怀疑过规则**

而她的做法是把**自己**放到被检查的那一侧,然后量。
她没有问「这条规则对不对」,她问「这条规则对谁成立」。

## 修法:从分支名推席位,不写死作者

`packet/<席位>/...` → 那个席位。推不出席位时(在集成线上、游离头),规则**整体不生效**。

### 改的时候又踩两个坑,都是自己测出来的

**一、空席位名会拦死集成线。** 我第一版写成「推不出席位时,自己的目录匹配不上,
于是走第二条,判成别人的」。实测:在集成线上提交会把**每一个**席位的文件都判成别人的,
而集成线本来就要跨目录 —— 那会让所有合并都被这条守卫拦死。
**没有依据时选择拒绝,会在最需要放行的地方拦死一切。**

**二、分支变量取晚了。** 第二条规则要靠分支推席位,而那个变量在文件后半段才赋值,
第二条规则读它时是空的,`set -u` 下直接崩。挪到开头。

七个方向实测:六个席位各提交自己的文件全部放行;她的分支扫进 Mira 的文件仍然拒绝;
集成线上跨目录放行;自检两个方向都触发。

## 规矩

1. **写完一条关于集合的规则,问一句:这条规则对谁不成立?**
   如果不是「对谁都不例外」,那就要说清例外是谁、凭什么。
2. **写守卫的时候,把自己也写进被检查的那一侧,然后量。**
   我写了六个方向的测试,唯独没测「别人用它会怎样」。
3. **「自己的目录」不是常量,是从上下文推出来的。** 写死作者的那一行,
   和写死一个数字是同一类错误:它会在作者换人之后开始骗人。
4. **没有依据时不拦。** 一条守卫在推不出依据时必须放行,
   否则它会在最需要它的地方(集成线)拦死一切。
