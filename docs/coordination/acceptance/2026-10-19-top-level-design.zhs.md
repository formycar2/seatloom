## 1. 产品命题与范围

SeatLoom 是一个**带可回溯证据的受管辖工作系统**，不是「一个终端仪表盘，外加任务、聊天、文件、记忆  
几套彼此不相干的集合」。它的中心闭环是：

**观察工作 → 把它记下来 → 解释当前处境 → 取得被授权的决定 → 执行 → 记录实际结果。**

这份设计把已交付的能力审计抬升成一套垂直架构。它不复述那份十一个标签页的清单，不改变你已经批准的  
方向，不规定实施步骤，不派单，也不授权任何界面改版。**一层是一项职责，不是一个新页面、新服务或新  
数据库。** 同一个现有组件可以承载多项职责，但它的写命令和读路径必须保持可分离。

审计确立了两个塑造了这份设计的事实：当前的进度类展示同时在看派单（dispatch）和工作项（workitem），  
却没有一个统一含义；而现有的验收区是最接近真实决策面的东西。这份设计保留后者，并通过对**一份解释  
契约**授予指标权威（而不是让各个控件各自定义），来解决前者。

## 2. 五层，职责互斥

之所以需要五层，是因为「活动、持久证据、解释、授权、呈现」这四类东西的保证强度不一样。把活动和  
授权并在一起，一个智能体就能自己批准自己；把解释和记录并在一起，一个推断就变成了历史；把呈现和  
其中任何一个并在一起，每一屏都会自己发明一套真相。

| 层              | 它回答的用户问题                      | 输入                                              | 输出与消费者                                             | 它**不**负责什么                                       |
| -------------- | ----------------------------- | ----------------------------------------------- | -------------------------------------------------- | ------------------------------------------------ |
| **A. 执行与观察**   | 实际跑了什么、改了什么、说了什么？             | 被授权的工作命令；harness/进程输出；源存储；真实动作回执                | 原始观察、产出的对象、实际结果 → 交给 B                             | 不决定谁有权批准；不解释项目整体状况；不把「终端很热闹」等同于交付进度。             |
| **B. 权威记录与证据** | 记录了什么、谁记的、凭什么？                | 经校验的观察/结果；被准入的生命周期事件与引用；源/归档清单                  | 不可变的事件历史、带上下文的主体身份、可解析的证据；维护好的当前态投影 → 给 C，校验 → 给 D | 不凭空补造缺失的观察；不把推断归类成原始证据；不统计用户义务；不因为索引了就宣称拥有源文件。   |
| **C. 工作解释与查询** | 这些记录**现在**意味着什么，我们知道什么、不知道什么？ | B 的历史与当前投影、显式的对象关系；已记录的治理策略                     | 一份带作用域和时间戳的工作/待办/血缘读模型 → 给 E；事实/候选/证据 → 给 D        | 不授权、不执行动作；不凭空制造派单与工作项之间的关联；不因为一行被卡住就推断出存在用户决策。   |
| **D. 治理与决策**   | 谁必须决定、哪些选项合法、之后允许做什么动作？       | C 解释出的候选；B 的当前事实与证据；行为者身份、权限与策略；显式的人工或受授权监督者的决定 | 经校验的决定记录 → 给 B；被授权的命令 → 给 A；拒绝/返工 → 给 C/E          | 不篡改结论；不悄悄替人做选择；不把「已授权的命令」报成「已执行完」；不提供自己另一套进度计数器。 |
| **E. 呈现与交互**   | 我在这里该看什么、该做什么？                | C 的读模型；D 允许的动作与前置条件；经 B/C 解析的证据视图               | 清楚的处境与解释 → 给用户；显式的用户请求/决定 → 给 D                    | 不在本地裁定策略；不直接写持久状态；不发明新鲜度或健康度；不把后端能力缺失当成「本地保存成功」。 |

### 不重叠，也不留空

A 拥有**效果**，B 拥有**什么被持久记录**，C 拥有**含义与查询**，D 拥有**权限与决定的有效性**，E 拥有  
**沟通与输入**。一个决定的「含义」和「允许的动作」是两件事：C 可以描述「有一项待验收」，但只有 D 能  
校验并落定人的验收；B 负责持久化，E 只负责呈现。

归档浏览器、文件浏览器、知识视图都坐在 E；它们的源指针和记录在 B；检索、源解析、记忆关系在 C。现有的  
监控/任务视图同样在 E。监督者对话框是**由 D 支撑的 E 的输入**，不是多出来的第六个「监督者形状」的数据层。  
终端镜像只是 E 望向 A 的一扇窗，不是 C 对进度的权威。这样就把审计里那张全貌表都安置掉了，而没有给每个  
标签页配一套架构。

## 3.「唯一真相源」是什么意思

**B 是「被记录的活动与证据」的唯一权威边界。C 是「对外发布的解释与指标」的唯一权威。E 两者都不是。**  
这不等于「把所有字节塞进一张 SQL 表」，也不等于「现在每张对象表都已经能从账本重建」。

| 主张                   | 权威在哪                        | 后果                                        |
| -------------------- | --------------------------- | ----------------------------------------- |
| 某个活动/决定发生过，且归属于某个行为者 | B 中的权威事件历史 + 显式引用           | 当前投影或终端文字不得改写历史含义。                        |
| 源代码/文档/原始记录里确实是这些字节  | 它指定的源存储或已记录的不可变版本/摘要，经 B 代表 | 数据库索引是定位符，不是替代源。源缺失或被改动要**报告**，不能用摘要重建。   |
| 这是当前受管辖的派单/验收状态      | B 中维护的领域投影，并连同依赖/策略经 C/D 读取 | 绝不因为「有一行被开出」或「有个分支名」就推断完成。                |
| 这条记忆说的是 X            | B 中带版本/状态标记的记忆记录            | 它的出处，以及「引用」还是「推断」的身份，必须与支撑它的证据区分开；记忆不是判决。 |
| 这些是用户待做的决定 / 这是工作进度  | C 基于 B 的、有文档的指标/读模型契约       | 同一作用域、同一 as-of 时间，任何位置显示同一结果。不允许控件本地另立公式。 |

一个计数由**含义 + 实体总体 + 作用域 + 状态谓词 + as-of 时间 + 来源/覆盖度**共同定义。「活跃派单」和  
「活跃工作项」是两个不同的计数，本来就可以不相等；不加说明地把两者都叫「团队进度」是禁止的。去重按  
已记录的身份/关联来做，不按标题。如果派单到工作项的关联根本不存在，就分别展示两个各自限定的总体，  
**不许相加，也不许假装一个覆盖了另一个**。

C 可以把同一个数字暴露在第一屏、项目总览或聊天上下文里。每一处都是**同一份契约的一种呈现**，不是各自  
独立的权威。覆盖不全、快照过期、读取失败、真的为空 —— 这是四种不同的状态。

## 4. 顶层图与依赖方向

```text
        外部源 / harness / 仓库 / 运行时
                      | 真实观察 / 结果
                      v
                 A. 执行与观察 <------ 被授权命令 ------ D. 治理与决策
                      |                                    ^        |
                      | 事实 + 证据                        |        | 已准入的决定
                      v                                    |        v
                 B. 记录与证据 ---------- 事实/当前校验 -------+
                      |
                      | 不可变历史 + 当前投影 + 指针
                      v
                 C. 解释与查询 ---- 解释后的候选 --------> D
                      |                                    ^
                      | 处境 / 待办 / 血缘                 | 请求或决定
                      v                                    |
                 E. 呈现与交互 -----------------------------+
                      |
                      v
              用户：理解 / 查看 / 选择

证据侧路：E 请求详情 -> C 经 B 解析 -> 原始源/版本。
没有 E -> B 的直接持久写。没有 A -> 用户批准的权威捷径。
```

这些箭头是契约和依赖，不是必须串行执行的服务链。D 可以重新回查 B，而不信任一份过期的 C/E 快照。A 可以  
在没有前置用户请求的情况下发出观察。读源文件不必把记录正文抄进权威账本。查询证据不是执行命令。

### 4.1 从某个席位的原始进程，到用户能看见的东西

A 观察到一次工具结果或一个产出的对象。B 记录被准入的带类型事实、上下文与源指针。C 只挂接已记录的关系，  
并在指定作用域/时间上解释状态与血缘。E 展示工作结果或证据放大视图。镜像终端可以作为原始细节直接出现在  
E 里，但**那个观察本身不构成工作完成**，除非受管辖的记录支持它。历史记录是通过 B 的索引归档边界、以及 C  
的只读回放入口的，而不是被伪造成过去的权威事件。

### 4.2 从判决或产品决定，到被执行的活

- **技术判决：** 评审者 A 给出带证据的结论。D 校验是谁发的、针对哪件事；B 记录该判决。C 解释它。这个判决  
  是后面**人类决定**的证据，它本身**不是**那个人类决定。
- **人的验收/产品选择：** E 把显式选择、身份、目标对象，以及当时展示的版本/上下文提交给 D。D 校验权限与  
  当前前置条件，准入或拒绝。决定被持久记录在 B；被授权的下游活被送到 A。动作的实际成败经 A/B 回来，再由  
  C/E 呈现。
- **带 git 合并的验收：** 校验先于合并。只有实际合并结果已知后才记录结果。git 和数据库是两个系统：这份  
  设计**不**声称一个原子事务跨越两者。效果与回执之间崩溃，是一个需要核对的**未知结果**，不是伪造的成功，  
  也不是自动重试合并。
- **没有仓库时：** 产品决定照样可以被记录、被派发，只是没有 git 合并这个动作可执行。动作能力是显式声明  
  的，而不是把 git 当成普适前提。
- **拒绝/纠正：** 记录拒绝与理由、以及被授权的返工；不许悄悄改写历史判决或原始用户选择。重试与重发保留  
  身份与出处。

每一次状态迁移只改变一件事：A 改变世界；B 记录它；C 解释它；D 授予或拒绝权限；E 让用户理解并选择。  
**「命令已排队」「操作成功」「结果已记录」「能力已安装」是四个不同的状态。**

### 4.3 证据是共享的，但它的权威不复制

所有层都可以在自己的权限边界内**引用**证据。B 拥有准入、出处、留存与源解析；C 提供有界查询；D 要求动作  
有足够有效的支撑；A 消费被批准的上下文；E 展示渐进披露的细节。**不要把证据复制到每一屏变成各自的真相。**  
索引和摘要可以是派生的，但必须指向同一个源/版本，并标明是派生。未知的关系保持未知。敏感原始内容不会  
仅仅因为摘要可见就自动可见。

## 5. 五条可执行的归位与存在性规则

1. **效果/权限判定：** 如果它会改变持久状态或外部系统，它就是一条由 D 授权、带 B 回执的 A 命令。如果它  
   只读、只描述，它就属于 C/E。**本地表单改动能满足保存契约吗？不能。** 测试必须能区分「已授权、已执行、  
   已记录、结果未知」。
2. **指标身份判定：** 加一个数字之前，先声明它的总体、谓词、作用域、as-of 时间与权威的 C 契约。如果另一个  
   视图展示同一指标，比对它们的契约身份与结果。公式不一致就算失败；总体不同就必须有不同标签。**没有声明  
   分母/覆盖度的「进度」不允许发布。**
3. **决定义务判定：** 一个「待用户决定」的条目，需要在 B/D 里有显式目标、允许选项、被授权的决定者、  
   待定/已定状态、证据与下游后果。仅有一条消息、一次读取失败、一条被卡住的派单，都通不过这条判定。  
   缺决定者或缺关系要**报告出来**，不是自动归到人头上。
4. **证据与状态判定：** E 展示的每一条主张，都要经 C 解析到 B/源，或明确标注为「推断/不可用」并带作用域与  
   新鲜度。故障测试必须能区分「空、不全、过期、不可用」。**渲染时钟或写死的绿色百分比一律不合格。**
5. **入口正当性判定：** 一个拟议界面必须满足其一 —— 呈现共享的工作/待办契约；接受一次受管辖的动作；或提供  
   一个不同的证据/上下文放大视图并能回到同一份工作。如果它只是重复同一契约而没有独立的用户任务，就复用  
   现有呈现；如果它绕过 B/C/D，就拒绝。**需要新增导航/交互的，等用户批准，而不是本文档批准。**

## 6. 第一屏的顶层位置

**用户落在 E 上，看的是 C 那份共享的「工作与待办」解释，旁边是 D 支撑的动作。** 用户不落在原始执行 A、  
不落在存储模型 B、也不落在另一个平行的「监督者壳」里。这和已经选定的方向完全一致：

- **全队在干什么：** 当前受管辖的工作，带 C 给的归属/状态/覆盖度。终端的活跃度和席位的在场是**上下文**，  
  不是进度的替代品。
- **什么卡着：** 由 C 评估出的前置条件与阻塞，并在明确已知时给出下一步归谁。预期产出者的数据缺失就保持  
  未知；不许从事件 id 去猜。
- **什么需要我决策：** 由 D 定义、C 解释的待办义务，而不是所有告警、内部记忆事件或每一条被卡住的任务。  
  验收只是其中一类，不是全集。

审计里那个判&#x65AD;**「派单页 + 验收区是最接近的现有锚点」依然成立**。它的组件布局不等于架构：那些现有区块  
应当去消费这份共享契约，而不是去定义它的含义。当前项目范围内的数据不能被悄悄改标成「全舰队」；舰队级  
聚合要保留项目归属并声明覆盖度。历史、知识、文件、原始终端，都是从这个处境出发的上下文放大。监督者  
对话框是输入/讨论的伴随物，不是第二个独立的仪表盘权威。

本文档**不**指定新的第一屏布局或导航。现有区块与信息架构原样保留。镜像作为主界面是过渡态，在终态里它  
依旧是原始诊断细节。证据回放**不**因为它实现放在一个更老的目录里就变成过渡态。

## 7. 用户选择 —— 与技术契约分开列

以下不是实施任务，也不重开已经定下的三个第一屏问题：

- **默认作用域：** 建议是全队视图、保留各项目身份，用现有的项目选择来收窄。当前锚点是项目本地的。在改变  
  「打开产品先看到什么」之前，请先确认默认作用域；在此之前，不许凭空造出跨项目的义务。
- **内部记账的展现程度：** 记忆召回/话题记账在事件放大视图里是否默认折叠。建议：它不该挤占第一屏上的  
  待办工作/决定，但作为证据仍可查。具体默认展开到什么程度由你定。
- **可见的收敛：** 架构上建议一个进度含义、一条受管辖的输入路径。但**哪一个重复入口继续可见、现有快捷方式  
  归谁**，都是用户的选择，在任何导航删除或改派之前先定。

单一指标契约、证据与决定的区分、禁止本地直接保存 —— 这些是架构职责，不是需要用户去解的问题。派单路由、  
集成、权限授予与闸门决定仍归 Aegis；本文档既不派发也不执行其中任何一项。

## 8. 证据基础、当前缺口与限度

已完成的能力审计是基线，不是一份新的清单。它测的是：传递可达性、上游事件顺序、当前作用域的注水、仪表盘  
计数器不一致、全局汇总用假数据、以及保留下来的本地表单。**这些正是这套分层必须防住的具体失效，但它们  
不是「共享解释已经实现」的证据。**

另外在干净的 `track@cfda740` 上做的源码核对确认：核心事件追加路径显式维护投影；派单生命周期走的是事务  
感知的追加原语；验收命令在对外合并之前校验判决值与主体；意图规划只有一个事实收集器并返回 `wrote:false`；  
归档清单指向磁盘上的原始字节。这些核对支撑的是**职责边界**，不是完整覆盖：遗留表/读路径仍然并存，  
监督者消息投递里还有一条打桩的注入分支，且并非每个投影今天都被证明可重放。

2026-09-30 那批设计评审区分了「活动/对象/上下文」、源自有字节、带类型的活动 vs 原始/进程证据、历史账本  
vs 当前投影。它们被标为草案引用：本文档使用其中有用的区分，但不把每一条提案说成已批准或已上线。**这里的
