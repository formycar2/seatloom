### Finding — `append_supervisor_message` bypasses the write API

Reported by Nimbus, **verified independently by me** at
`crates/seatloom-core/src/db/repositories.rs:405-433`:

- the `canonical_events` INSERT (`:421`) does **not** name `schema_version` → depends on `010:87`
  `DEFAULT 1`;
- the `event_object_refs` INSERT (`:429`) does **not** name `role` → depends on the `context`
  default;
- it writes only a `ref_type='seat'` ref, so **every supervisor message is a zero-subject event** —
  exactly what the step-2 `EventDraft::validate` now rejects.

So it is the **sole remaining consumer of both `010` defaults**, which blocks the P1 cleanup to drop
them — and, more than that, it produces events the write API itself would refuse. No DB constraint
is breached (`010:332` is *at-most*-one subject, and zero satisfies it), so nothing breaks at
runtime today. The asymmetry is the finding.

**Ruling: out of scope for step 2.** Nimbus was told not to expand the packet and not to fix it, and
to document it as a named finding with line anchors. It gets its own follow-up packet. Nimbus
disclosed it rather than widening scope silently or staying quiet — the behaviour the rules want.
