## 一、MVP 的核心命题

SeatLoom 不是一个需要 6 个月才能判断成败的产品。它的核心价值假设可以在一个明确定义的场景中被验证或证伪。

**MVP 要回答的唯一问题：**

> 对于一个已经在用 3-5 个 CLI agent 工具的重度用户，SeatLoom 能否在不要求改变工作方式的前提下，显著减少上下文搬运、保住跨工具连续性、并提供可回溯的项目工作面？

这不是"产品是否完整"的验证，而是"产品是否成立"的验证。

## 二、MVP 范围：收束到最小可验证单元

### 2.1 一个核心场景

**单人 + 4 个 AI Seat + 2 个主力 CLI 工具 + 1 个本地代码仓库**

具体配置：

| 要素 | MVP 取值 | 说明 |
|------|---------|------|
| 用户数 | 1 人 | 独立开发者 / AI-native founder |
| Seat 数 | 4 个 | Lyra（需求）、Nimbus（架构/实现）、Flux（测试）、人类（决策/审批） |
| 主力工具 | Codex CLI + Claude Code | 当前 AI 编程社区用量最大、能力最成熟的两个 CLI agent |
| 辅助工具 | 1 个（Cursor CLI 或 Gemini CLI） | 仅用于验证跨工具 rehydrate，不做深适配 |
| 代码仓库 | 1 个本地 Git 仓库 | 真实项目，非 demo |
| 工作模式 | 至少经历 1 次完整的"需求 → 实现 → 测试 → 修复"循环 | 覆盖完整的协作链路 |

### 2.2 三个杀手能力

| 编号 | 能力 | 对应铲子 | 一句话描述 |
|------|------|---------|-----------|
| K1 | 多 Session 观察与留痕 | Attach + Capture + Replay | 接住 4 个 CLI 窗口，自动生成 timeline 和 inbox，不再靠脑记。 |
| K2 | 跨工具上下文重建 | Rehydrate | 一个 Seat 从 Claude Code 切到 Codex 时，系统自动组装 LaunchPack。 |
| K3 | 结构化 Handoff 草稿 | Capture + Rehydrate（轻量） | 从 transcript/diff/test 自动生成交接草稿，替代人工复制粘贴。 |

**明确不做（MVP 范围外）：**

- 不做完整 PolicyPack 治理体系
- 不做 daemon / overnight 自治模式
- 不做 Pipeline 编排引擎（仅保留最小 handoff 触发）
- 不做 Memory / Skill Growth 闭环
- 不做 ORCH / CAO 等第三方编排框架适配
- 不做多用户 / 远程协作
- 不做成本统计和预算控制
- 不做 Docker workspace 隔离

## 三、可量化的验证指标

### 3.1 主指标：上下文搬运减少

| 维度 | 定义 |
|------|------|
| **指标名称** | 上下文搬运次数减少率 |
| **目标值** | ≥ 50% |
| **统计对象** | 用户在一段完整 WorkItem 推进中，在 agent 窗口之间手动执行的"上下文搬运动作" |
| **搬运动作定义** | 以下任一操作计为 1 次：① 复制粘贴代码/错误信息/输出摘要到另一个窗口 ② 手动编写一段交接说明文字 ③ 口头或文字向另一个窗口重复解释当前状态 |
| **Baseline 建立方式** | 在没有 SeatLoom 的情况下，让用户完成一个典型 WorkItem（如"实现一个带验证的用户注册接口"），通过录屏和操作日志统计搬运次数和总耗时 |
| **对照测量方式** | 同一用户，同类复杂度的 WorkItem，使用 SeatLoom 的 Mode 1（Assist 档），统计搬运次数 |
| **判定标准** | 对照组的搬运次数 ≤ Baseline 的 50% |

### 3.2 辅助指标

| 指标 | 目标值 | 测量方式 |
|------|--------|----------|
| **跨工具切换恢复时间** | ≤ 5 分钟 | 从用户发出切换指令到新 session 接收到完整 LaunchPack 且产出第一个有意义响应的时间间隔。连续测量 5 次取中位数。 |
| **Session 中断恢复成功率** | ≥ 80% | 模拟 5 次 session 异常中断（杀进程、Ctrl+C、网络断开），检查能否通过 Checkpoint + ContextPack 恢复并继续完成原任务。 |
| **早晨收束效率** | ≤ 3 分钟获取全局状态 | 用户在隔夜后打开 SeatLoom，从查看 inbox 到能够准确回答"哪些任务完成、哪些卡住、哪些待审批"的时间。 |
| **两周后决策回溯覆盖率** | ≥ 80% | 在已完成 WorkItem 中随机抽取 5 个，检查是否能够完整还原：谁触发 → 在哪个 session → 依据什么上下文 → 经过什么交接 → 产出什么。 |
| **Mode 0 上手时间** | ≤ 10 分钟 | 新用户从安装 `seatloom` CLI 到在 timeline 中看到第一个有意义条目（如 "Session attached: Nimbus/Claude Code"）的时间。 |
| **Mode 0 需学概念数** | ≤ 1 个 | 用户在看到首次价值之前，需要理解的新概念数量。目标：只需要知道 `seatloom attach` 一条命令。 |

### 3.3 指标优先级

| 优先级 | 指标 | 理由 |
|--------|------|------|
| **P0 必达** | 上下文搬运减少 ≥ 50% | 这是用户第一痛点，也是产品核心价值 |
| **P0 必达** | Mode 0 上手 ≤ 10 分钟 + 概念 ≤ 1 个 | 如果用户进不来，其他指标无意义 |
| **P0 必达** | 跨工具切换恢复 ≤ 5 分钟 | 这是 SeatLoom 最有辨识度的能力 |
| **P1 重要** | Session 中断恢复 ≥ 80% | 影响可靠性感知 |
| **P1 重要** | 早晨收束 ≤ 3 分钟 | 影响日常使用体验 |
| **P1 重要** | 两周回溯覆盖率 ≥ 80% | 影响长期信任 |

## 四、四个生命体征的场景化验证

这四个场景是 MVP 的终极验收关卡，不是"功能测试用例"而是"场景通过标准"。

### 生命体征 1：跨工具切换不需重写上下文

**测试场景**：
> Nimbus 在 Claude Code 中完成了用户认证模块的架构设计（产出：设计文档 + 接口定义）。现在需要切换到 Codex 来实现具体代码。

**通过标准**：
1. 用户发起切换指令（如 `seatloom session launch --seat nimbus --runtime codex --from-session SES-01`）
2. 系统在 5 分钟内自动组装 LaunchPack，包含：设计文档摘要、接口定义、当前 branch、相关 acceptance criteria
3. Codex 新 session 的第一个响应显示出对架构上下文的理解（而非泛泛的"请告诉我更多信息"）
4. 整个过程中，用户**不需要**向 Codex 手动输入任何关于架构设计的说明

**失败条件**：
- 新 session 问了 3 个以上已存在于 LaunchPack 中的信息
- 用户不得不手动复制粘贴设计方案才能让 Codex 理解任务

### 生命体征 2：Session 中断后项目不断

**测试场景**：
> Flux 正在 Codex 中运行测试套件，发现 3 个失败用例。此时 Codex session 因网络波动意外中断（或用户主动关闭了终端窗口）。

**通过标准**：
1. SeatLoom 保留了 Flux session 的 Checkpoint（包含最近的测试输出和错误分析）
2. 用户可以基于该 Checkpoint 恢复一个新的 Flux session
3. 新 session 继续分析测试失败原因，不需要用户重新描述"刚才做到哪了"
4. 整个过程中没有丢失超过 5 分钟的实质性工作产物

**失败条件**：
- 恢复后 Flux 完全不知道之前发生了什么
- 丢失了关键的错误分析或修复尝试记录
- 用户需要从头描述问题和已做尝试

### 生命体征 3：早晨一眼看全局

**测试场景**：
> 用户在昨晚同时启动了 4 个 Seat 分别处理不同任务。早上回到电脑前。

**通过标准**：
1. 打开 SeatLoom TUI/Dashboard（或执行 `seatloom inbox`），在 3 分钟内获取以下信息：
   - 哪些 WorkItem 已完成（附带产物摘要）
   - 哪些 Session 仍在运行或已中断
   - 哪些 Handoff 等待审批或接收
   - 哪些任务被卡住（blocked / failed）及原因
2. 用户不需要切换回各个终端窗口去查看 stdout 滚动历史
3. 信息呈现清晰到用户可以立即做出"先处理哪个"的决策

**失败条件**：
- 用户仍然需要逐个检查 4 个终端窗口才能知道全局状态
- Inbox/Timeline 信息混乱，无法分辨优先级
- 信息存在明显遗漏（某个 seat 的工作完全没有被捕获）

### 生命体征 4：两周后可回溯决策链

**测试场景**：
> 两周前，Nimbus 在一个 Codex session 中修改了数据库迁移脚本。今天生产环境发现该迁移导致了数据不一致。需要追溯当时是谁、为什么、依据什么做了这个修改。

**通过标准**：
1. 在 SeatLoom 中能够找到该修改对应的 WorkItem 和 Session
2. 能够看到当时的 LaunchPack（Nimbus 带着什么上下文启动的）
3. 能够看到修改的 diff、关联的 Handoff 和测试结果
4. 能够回答：
   - 这个修改是 Nimbus 自主决定还是有 Handoff 指令？
   - 修改前是否有测试？测试是否通过？
   - 是否有 review gate？是否经过审批？
   - 修改后是否有 Flyway/Prisma 迁移验证？
5. 整个回溯过程 ≤ 10 分钟

**失败条件**：
- 找不到该修改属于哪个 WorkItem/Session
- 关键决策节点缺少证据（如只有 diff 没有上下文）
- 责任链断裂（无法确认是谁触发了这个修改）

## 五、止损条件（MVP 失败标准）

以下任一条件触发，MVP 视为失败，需要重新审视产品方向，而非继续投入工程资源：

### 核心止损线（任一触发即判失败）

| 编号 | 止损条件 | 判断逻辑 |
|------|---------|----------|
| **STOP-1** | 两个主力工具的 attach + capture 成功率 < 90% | 如果连"接住现有 session 并稳定采集"都做不到，后续所有能力都无从建立。这说明适配层策略需要根本性调整。 |
| **STOP-2** | 上下文搬运次数减少 < 30% | 如果核心痛点没有显著缓解，产品不成立。50% 是目标，30% 是最低可接受线。低于 30% 说明系统没有创造足够的增量价值。 |
| **STOP-3** | 跨工具 rehydrate 后的任务完成效率低于手动搬运上下文 | 如果"系统帮忙重建上下文"比"用户自己复制粘贴 + 写摘要"更慢或更差，说明 ContextPack Builder 的设计有根本缺陷。 |
| **STOP-4** | Mode 0 用户在前 30 分钟内放弃使用 | 如果用户在上手阶段就流失，说明渐进采用模型的第一层门槛仍然太高。 |

### 次级止损线（累计触发两条判失败）

| 编号 | 止损条件 |
|------|---------|
| **STOP-5** | Session 中断后恢复任务的完成率 < 50% |
| **STOP-6** | 两周后回溯时，超过 50% 的关键决策节点找不到证据 |
| **STOP-7** | 用户反馈"用了比不用更累"的比例 > 30% |

### 止损后的行动

如果触发止损条件，不要立即放弃，而应按以下顺序排查：

1. **是适配层问题还是产品设计问题？**（如果是 wrapper_capture 不够稳定，可以优化适配器；如果是整个 attach 理念不被用户接受，则需要 pivot）
2. **是 MVP 范围问题还是产品本质问题？**（也许 MVP 选的 2 个工具恰好是最难接的两个，换工具可能完全不同）
3. **是用户画像问题还是价值假设问题？**（也许目标用户根本不是"已经在用多 CLI 的重度用户"，而是另一群人）

## 六、验证时间线

| 阶段 | 时间 | 目标 | 产出 |
|------|------|------|------|
| **Phase 0: 适配器验证** | 第 1-2 周 | 确认 Codex 和 Claude Code 可以被 wrapper_capture 稳定附着和捕获 | Adapter 能力矩阵 + capture 稳定性报告 |
| **Phase 1: 单工具留痕** | 第 3-4 周 | 完成 Mode 0：单用户 attach 2 个 session，实现 timeline + inbox | 可运行的 seatloom CLI + .seatloom 目录结构 |
| **Phase 2: 跨工具重建** | 第 5-6 周 | 完成 Mode 1：rehydrate 能力 + ContextPack Builder 最小版 | LaunchPack 组装 + 跨工具切换成功案例 |
| **Phase 3: Handoff 草稿** | 第 7-8 周 | 完成 Mode 2 基础：从 transcript/diff 自动生成 Handoff 草稿 | Handoff 草稿生成 + inbox 整合 |
| **Phase 4: 验收测试** | 第 9-10 周 | 完成四个生命体征的完整场景测试，对照五项核心指标 | 验证报告 + Go/No-Go 决策 |

## 七、Go/No-Go 决策框架

在 Phase 4 结束后，基于以下矩阵做出决策：

| 决策 | 条件 |
|------|------|
| **Go（进入 P1 开发）** | 全部 3 个 P0 指标达标 + 至少 2 个 P1 指标达标 + 无核心止损条件触发 |
| **Conditional Go（调整后继续）** | P0 指标至少 2 个达标，但需要 1-2 个 sprint 修复特定问题 |
| **Pivot（方向调整）** | 核心止损条件触发，但用户反馈显示"连续性痛点"确实存在，可能需要不同方案 |
| **No-Go（终止）** | 核心止损条件触发，且用户反馈显示"痛点不成立"或"解决方案从根本上不匹配" |

---

*这份文档不是对 SeatLoom 的承诺，而是对 SeatLoom 的考验。它描述的不是一个注定成功的产品，而是一个可以被证伪的实验。*
